# 아기 울음 육아 도우미 팀 개발 계약

계약 버전 1.0.0 · 결정일 2026년 9월 19일

이 문서는 사용자와 팀원이 제시한 두 착수 체크리스트의 결정을 통합한다. 추가로 제공된 `baby-care-implementation-tasks-A-v2.md`의 A-01~A-11을 대조했다. A는 윤정님인 웹·브라우저 담당, B는 사용자인 API·데이터·ML 담당이다. PRD v2와 기능명세서 v2의 P0 범위를 유지하며, 화면과 서버의 접점에서 아직 명확하지 않은 값을 이 계약으로 보충한다. 아래 결정은 이번 개발의 기준이며 실제 API 배포, 모델 성능 검증, 시험 계정 발급이 완료됐다는 보고는 아니다.

최신 구현 계획은 [A 업무 분담 v2.1](../docs/baby-care-implementation-tasks-A-v2.md)과 [B 업무 분담 v2.1](../docs/baby-care-implementation-tasks-B-v2.md)이다. v2.1이 추가한 A-12·A-13·B-14와 CHAT/CHAR 항목은 기존 계약을 보존한 후속 업무이며, 특히 상담 경로와 신규 보안 상태·오류는 이 계약과 OpenAPI를 함께 보완하기 전까지 계약 1.0.0에 포함된 것으로 간주하지 않는다. 이 안내는 API 필드·상태·동작을 변경하지 않는다.

## 1 기준과 담당

제품 범위는 PRD v2, 기능 동작은 기능명세서 v2, 연동 필드와 HTTP 계약은 이 폴더의 [OpenAPI 계약](./openapi계약.json)을 따른다. 명세서 표지의 연결 문서 v1.1 표기는 이전 개정의 잔재로 보고 본문의 v2 기준을 적용한다. 이번 결정으로 원본 문서는 수정하지 않았다.

| 항목                                        | 최종 책임                      | 상대방이 제공할 내용                           |
| ------------------------------------------- | ------------------------------ | ---------------------------------------------- |
| 식별자·상태·권한·오류·API·DB·RLS·Storage    | B                              | A가 필요한 화면 상태와 누락 필드를 제시        |
| 화면·폼·마이크·캐시·복구·출처 배지          | A                              | B가 상태값·샘플·모델 지원 정보를 제공          |
| 모델·전처리·정규화·추천 정책·실제 실행 출처 | B                              | A가 받은 값을 표시하고 실제 브라우저 동작 검증 |
| 사용자 문구·두 계정 인수 시험               | A와 B 공동                     | 같은 시나리오에서 화면과 서버 결과를 대조      |
| 계약 변경                                   | B가 스키마 수정, A가 영향 확인 | 같은 변경에 샘플·문서·화면 매핑을 함께 반영    |

계약 상태는 화면을 보고 추측하지 않는다. B가 서버 상태를 소유하며 A는 서버에서 받은 상태를 표현한다. 업로드 진행률, 폼 입력, 현재 탭의 마이크 상태는 A가 소유하는 로컬 상태다. 기존 필드 삭제·이름 변경·enum 추가·null 의미 변경은 A의 검토가 필요한 계약 변경으로 취급한다. 기존 선택 필드 추가는 하위 호환성을 확인해 반영한다.

[OpenAPI 계약](./openapi계약.json)은 A-01~A-11에서 사용하는 웹 연동 범위를 기계가 읽을 수 있게 정한 계약이다. 아기·멤버십·초대·동의·음원·사건·분석·기록·행동·반응·정규화·삭제·감지 세션·이전 사례·요약·패턴·알림을 포함한다. 로그인과 세션 갱신은 Supabase Auth 계약을 사용한다. 내부 학습 검수·묶음 API는 웹에서 호출하지 않으며 v2의 B 담당 범위와 인수 기준을 유지한다.

## 2 사용자와 아기 권한

아기당 활성 OWNER는 정확히 한 명이다. CAREGIVER는 초대 수락으로 참여한다. 한 계정은 현재 ACTIVE인 직접 생성 아기 한 명까지 소유하고, 초대받은 아기는 추가로 이용할 수 있다. 부모·조부모 등 관계명은 표시용이다. P0에는 소유권 이전이나 읽기 전용 역할을 추가하지 않는다.

| 동작                                 | OWNER                           | CAREGIVER                 |
| ------------------------------------ | ------------------------------- | ------------------------- |
| 공유된 기록·분석·확인 상태·안내 조회 | 허용                            | 허용                      |
| 기록·행동·상태·후속 반응 추가        | 허용                            | 허용                      |
| 본인 기록 수정·삭제                  | 허용                            | 허용                      |
| 다른 작성자의 확정 기록 수정·삭제    | 허용, 최초 작성자와 수정자 보존 | 금지, 후속 관찰 추가 가능 |
| 타인의 확인 전 초안 조회·수정        | 금지                            | 금지                      |
| 프로필·아기 공통 동의·보관 설정 변경 | 허용                            | 금지                      |
| 초대 발급·취소·구성원 제거·전체 삭제 | 허용                            | 금지                      |
| 개인 학습 참여 설정                  | 본인 것만                       | 본인 것만                 |
| 본인 나가기                          | 금지, `409 OWNER_REQUIRED`      | 허용                      |

권한은 JWT의 오래된 역할 값이 아니라 DB의 현재 멤버십과 아기 상태로 판단한다. 서버용 secret key를 사용해도 같은 검사를 한다. 같은 아기인지도 모든 연결에서 검사한다. 타인의 비공유 초안과 비구성원의 객체 접근은 존재 여부를 숨기는 404로 통일한다. 회원으로 참여 중이지만 관리 권한이 없는 동작은 403이다.

탈퇴 후에도 본인의 학습 동의 조회·철회와 본인이 신청한 삭제 작업 조회·본인 기여자료 삭제 신청은 가능하다. 이는 본인 이력에만 적용하며 아기 기록을 다시 열어주지 않는다. 운영·학습 검수 권한은 OWNER와 별개이며 보호자 화면에서 부여하지 않는다.

## 3 아기 전환과 초대 및 탈퇴

### 아기 전환

활성 `baby_id`는 현재 브라우저 탭의 선택이다. 서버에 저장하는 마지막 선택은 다음 로그인 기본값일 뿐 다른 기기의 화면을 강제로 바꾸지 않는다. 모든 요청은 경로 또는 본문에서 대상 아기를 명시하며, 서버의 마지막 선택을 암묵적인 쓰기 대상으로 사용하지 않는다.

전환 순서는 기존 감지 중지 → 음원 재생·마이크 종료 → 이전 범위의 요청 구독 해제 → 서버 권한 확인 → 새 아기 조회다. 취소할 수 없는 이전 분석은 원래 아기에 붙어 완료된다. 늦은 응답은 요청 당시 `user_id`·`baby_id`와 현재 범위를 비교해 다른 아기 화면에 적용하지 않는다.

캐시 키는 `(user_id, baby_id, resource, parameters)`로 고정한다. 이전 아기의 조회 캐시·재생 URL·로컬 미저장 초안·원시 음원은 전환 시 폐기한다. 미저장 입력이 있으면 계속 작성, 개인 초안 저장 후 전환, 버리고 전환 중 선택하게 한다. 서버에 저장된 개인 초안은 원래 아기의 작성자 전용 자료로 남고 그 아기에 돌아왔을 때 다시 조회한다. 로그아웃·다른 계정 로그인·권한 해제 때는 해당 캐시와 미전송 내용을 지우고 자동 저장·재전송하지 않는다.

### 초대

OWNER가 검증 대상 이메일을 지정해 24시간 유효한 일회용 링크를 발급하고 직접 전달한다. 토큰은 서버가 난수로 생성해 해시만 저장한다. 재발급은 이전 미수락 토큰을 취소한다. 링크를 받은 사람은 로그인과 이메일 검증 후 공유 범위를 수락한다. 수락과 멤버십 생성은 한 트랜잭션이다.

처음 보는 사람이 단순히 링크를 열었을 때 아기 기록은 노출하지 않는다. 이메일 불일치는 `403 INVITE_EMAIL_MISMATCH`, 만료는 `410 INVITE_EXPIRED`, 취소는 `410 INVITE_REVOKED`, 다른 작업으로 이미 사용된 초대는 `409 INVITE_ALREADY_USED`다. 같은 수락 요청의 재전송은 기존 성공을 반환한다. 이미 활성 구성원이면 `409 ALREADY_MEMBER`로 알린다.

초대 원문 토큰을 서버에 저장하지 않으므로 발급 응답의 링크는 최초 한 번만 제공한다. 같은 발급 요청을 재전송하면 같은 invite_id와 `invite_url=null`, `link_reissue_required=true`를 반환한다. 링크를 받지 못했거나 잃었다면 A가 재발급 동작을 제공하고, 새 요청으로 이전 링크를 취소한다. 링크 수락의 중복 방지와 링크 원문 재조회는 구분한다.

### 탈퇴와 제거

CAREGIVER 나가기는 `LEFT`, OWNER가 구성원을 제거하면 `REVOKED`다. 두 경우 기존 공유 기록은 남고 신규 접근은 차단한다. 같은 사용자가 다시 초대받으면 새 멤버십 ID를 만든다. 탈퇴는 학습 동의 철회나 본인 기록 삭제를 의미하지 않는다. 나가기 화면에서 별도 철회·삭제 경로를 함께 제공한다.

권한이 사라지면 신규 API 접근·업로드·재생 URL 발급·변경 구독을 차단한다. 이미 발급된 재생 URL은 최대 60초의 남은 수명 동안 동작할 수 있다. A는 현재 재생과 캐시를 즉시 지우되 이미 다운로드된 사본의 회수를 보장하지 않는다.

## 4 식별자와 공통 필드

| 대상                | 식별자                                     | 발급 주체 및 관계                                        |
| ------------------- | ------------------------------------------ | -------------------------------------------------------- |
| 사용자              | `user_id`                                  | Supabase Auth, 서버가 토큰에서 확정                      |
| 아기                | `baby_id`                                  | B, 아기와 OWNER 멤버십을 함께 생성                       |
| 구성원·초대·동의    | `membership_id`, `invite_id`, `consent_id` | B, 각각 아기·사용자·목적에 연결                          |
| 울음 사건           | `episode_id`                               | B, 시간상 이어지는 울음 묶음                             |
| 음원·업로드         | `audio_id`, `upload_id`                    | B, 하나의 음원에 재시도용 업로드 세션을 별도로 발급 가능 |
| 분석                | `analysis_id`                              | A가 UUID를 먼저 발급, B가 아기·요청자·본문을 검증        |
| 생활 기록·행동·반응 | `care_event_id`, `action_id`, `outcome_id` | B, 행동은 기존 생활 기록을 참조 가능                     |
| 원문 초안·정규화    | `entry_id`, `run_id`                       | entry는 B, run은 A가 먼저 발급                           |
| 삭제·감지 세션      | `deletion_job_id`, `session_id`            | B                                                        |
| 논리 요청·HTTP 요청 | `client_request_id`, `request_id`          | 전자는 A의 중복 방지 UUID, 후자는 B가 HTTP 요청마다 발급 |

식별자는 UUID로 고정한다. 전송 필드명은 snake_case다. 작성자·수정자·확인자는 클라이언트가 지정할 수 없다. 실제 행동한 사람인 `performed_by_user_id`는 별도 선택값이고 모르면 null이다. 사람 이름을 계정으로 자동 연결하지 않는다.

시각은 시간대가 포함된 ISO 8601로 받고 UTC로 저장한다. 실제 발생 시각 `occurred_at`, 수신 시각 `recorded_at`, 수정 시각 `updated_at`을 구분한다. 모르는 값은 null, 실제 0만 0이다. 수정 가능한 객체의 `version`과 원문 `input_revision`은 1부터 증가한다. 수량·길이는 음수를 허용하지 않고 최대 5분을 넘는 미래 시각은 422다.

## 5 상태와 전이

| 대상             | 상태                                                             | 확정 규칙                                                                 |
| ---------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Baby             | ACTIVE → DELETING → DELETED                                      | 삭제 실패여도 ACTIVE로 복귀하지 않음                                      |
| BabyMembership   | ACTIVE → LEFT 또는 REVOKED                                       | 재참여는 새 멤버십                                                        |
| BabyInvite       | PENDING → ACCEPTED 또는 EXPIRED 또는 REVOKED                     | 종료 상태에서 토큰 재사용 불가                                            |
| Consent          | NOT_GRANTED → GRANTED → REVOKED                                  | 재동의는 새 이력, 과거 이력 덮어쓰기 금지                                 |
| AudioAsset       | ALLOCATED → VERIFYING → READY 또는 REJECTED → DELETING → DELETED | 업로드 진행률은 로컬 상태, 검증 결과는 서버 상태                          |
| CryEpisode       | OPEN → CLOSED                                                    | 사건 종료와 분석 완료는 별개; 파일만으로 전체 울음 지속시간을 채우지 않음 |
| Analysis         | READY → RUNNING → COMPLETE 또는 ABSTAIN 또는 FAILED              | FAILED만 명시적 재시도로 RUNNING 전이                                     |
| CareEvent        | ACTIVE → DELETING → DELETED                                      | 수면 진행 중은 `ended_at=null`로 별도 표현                                |
| ActionAttempt    | ACTIVE → DELETING → DELETED                                      | 실제 수행 확인 때만 생성                                                  |
| 행동 후속 확인   | PENDING → RECORDED 또는 UNCONFIRMED                              | 반응 미입력을 성공이나 실패로 바꾸지 않음                                 |
| RawCareEntry     | DRAFT → NORMALIZING → REVIEW_READY → CONFIRMED                   | 실패 시 NEEDS_MANUAL_REVIEW, 수정 시 revision 증가                        |
| NormalizationRun | RUNNING → COMPLETE 또는 FAILED                                   | 원문·버전 변경 시 이전 결과 STALE                                         |
| DeletionJob      | PENDING → RUNNING → COMPLETE 또는 FAILED                         | 실패 후 같은 job으로 재시도, 삭제 차단은 유지                             |

AudioAsset은 보관 철회나 삭제 요청으로 ALLOCATED·VERIFYING·READY·REJECTED 어느 상태에서든 DELETING으로 갈 수 있다. REJECTED 파일을 교체하면 새 audio_id를 만든다. RawCareEntry와 관련 기록은 삭제 중·삭제됨 상태도 지원한다. 확정 원문을 직접 PATCH하지 않고 새 수정 초안을 만들며, 재확인 때 기존 기록 ID를 유지한다.

행동의 `RECORDED`는 반응을 입력했다는 뜻이다. 그 반응이 `UNKNOWN`일 수 있다. `UNCONFIRMED`는 관찰 결과를 입력하지 않고 이번 후속 확인을 닫았다는 뜻이다. 나중에 실제 반응을 추가하면 RECORDED로 바뀐다. 계획·부정·불확실한 행동에는 ActionAttempt를 만들지 않는다.

마이크 상태는 명세 v2의 IDLE·REQUESTING·LISTENING·CANDIDATE·CAPTURING·PAUSED·ERROR를 유지한다. 서버 감지 세션은 ACTIVE·STOPPED·EXPIRED이며 아기당 ACTIVE 하나만 허용한다. heartbeat 10초, 마지막 유효 heartbeat로부터 30초 후 만료다. 숨김·잠금·오프라인에서 관측을 중지하고 전경 복귀 때 사용자가 재개한다. 브라우저 타이머만으로 관측 시간을 늘리지 않는다.

## 6 분석과 응답 유실

P0는 명세 v2의 요청 내 실행 방식을 유지한다. 업로드 완료 후 A가 `analysis_id`와 `client_request_id`를 만들고 분석 POST를 호출한다. B는 작업 행과 실행 잠금을 먼저 저장하고 최대 45초 안에 처리·결과 저장 후 200으로 최종 Analysis를 반환한다. 실행 lease는 60초, A의 최초 대기 제한은 65초로 정한다. READY는 음원 검증을 통과해 분석 요청 가능한 상태이며 실제 분석 행은 POST가 등록한다.

응답이 유실되면 같은 `analysis_id`를 GET한다. RUNNING이면 2초 간격으로 조회하고 자동으로 새 분석을 만들지 않는다. lease가 끝난 실행은 B가 FAILED로 확정한다. FAILED 후 사용자가 재시도하면 같은 analysis_id, 새로운 중복 방지 키, `expected_attempt`로 시도 번호를 올린다. 이전 실행 토큰의 늦은 결과는 저장하지 않는다. ABSTAIN 뒤 다시 녹음하면 같은 episode에 새 audio_id와 새 analysis_id를 연결한다.

GET 자체가 성공하면 HTTP 200이다. 그 안의 `status=FAILED`는 저장된 분석 작업의 실패다. 인증·검증·모델 준비 등의 이유로 요청 자체를 수락하지 못했으면 4xx 또는 503 오류를 반환한다. 이 경우 생성하지 않은 분석 ID가 있다고 주장하지 않는다. 404 조회가 나오면 요청 미등록 가능성을 안내하고 같은 생성 ID와 중복 방지 키로 원 요청을 다시 보내도록 한다.

| 상태     | 화면 문구와 동작                              | 결과 필드                           |
| -------- | --------------------------------------------- | ----------------------------------- |
| RUNNING  | 분석 중, 현재 단계 표시                       | 결과·오류는 null 또는 빈 배열       |
| COMPLETE | 후보와 근거·확인 행동 표시                    | 평가 통과 지원 후보 최대 3개        |
| ABSTAIN  | 판단을 유보했어요, 사유와 재녹음·기록 이동    | 후보 빈 배열, `abstain_reason` 필수 |
| FAILED   | 분석을 완료하지 못했어요, 복구 가능 시 재시도 | `failure` 필수, 유보 사유 null      |

`quality_status`는 PENDING·PASS·INSUFFICIENT·INVALID, `cry_detected`는 true·false·null이다. 유보 사유는 NO_CRY·LOW_QUALITY·INSUFFICIENT_AUDIO·LOW_CONFIDENCE·UNSUPPORTED_SCOPE로 고정한다. 시간 초과·모델 오류를 유보로 세지 않는다. 내부 후보 점수는 실제 원인 확률처럼 화면에 백분율로 표시하지 않는다.

분석 응답은 식별자·상태·stage·attempt_no·lease, 품질·울음 여부·후보·유보 사유·실패, 사용한 모델·전처리·라벨 버전, 맥락 스냅샷과 안내, 출처를 포함한다. 맥락만 재계산하면 새 snapshot·recommendation을 만들고 기존 audio_candidates와 모델 버전은 유지한다. 당시 기록 버전은 일반 수정으로 덮어쓰지 않는다.

## 7 기록과 정규화

선택지만 입력하면 고정 코드 검증과 수행 확인 후 저장할 수 있다. 자연어가 있으면 RawCareEntry를 먼저 저장하고 정규화 결과를 사용자에게 보여준 뒤 확인 저장한다. 원문 최대 길이는 2000자, 정규화 요청 제한은 20초, lease는 30초, A의 대기 제한은 35초로 정한다. 응답 유실 시 run_id로 조회한다.

초안에는 원문·선택값·input_revision·정규화 결과·근거·미해결 항목을 포함한다. actions는 PERFORMED·PLANNED·NEGATED·UNCERTAIN을 구분한다. states·outcomes·caregiver_interpretations는 별도 배열이다. 근거 위치는 원문 Unicode 코드포인트의 시작 포함·끝 제외 범위다. A는 JavaScript UTF-16 인덱스를 그대로 보내지 않는다.

확인은 `input_revision`, `run_id`, `normalization_mode`, 사용자가 확인한 내용과 연결 기록의 `version`을 함께 검사한다. RULE 또는 MANUAL이면 run_id=null이고 같은 코드·출처 검증을 적용한다. 한 트랜잭션으로 생활 기록·행동·상태·반응·라벨을 확정한다. 실패하면 부분 기록을 남기지 않는다. 초안이 오래됐거나 연결 기록이 바뀌었으면 409와 최신 값·수정 초안을 비교하게 한다.

미해결 항목 중 UNKNOWN_VALUE·UNKNOWN_TIME은 사용자가 모름을 확인한 채 저장할 수 있다. 선택과 문장 사이의 CONFLICT, 허용하지 않은 코드, 근거 누락은 해소하기 전 확인 저장을 막는다. 저장하지 않을 초안은 작성자만 삭제할 수 있다.

원문이 수정된 뒤 도착한 예전 LLM 응답은 STALE로 처리한다. 확인 전 초안은 공동 타임라인·추천·학습에 들어가지 않는다. OWNER가 다른 사람의 확정 기록을 고치면 최초 작성자·수정자·확인자를 모두 보존한다. 수정 초안은 수정자만 볼 수 있다.

생활 기록과 사건의 행동 연결은 `(episode_id, care_event_id)` 중복을 막는다. 새 생활 기록과 기존 기록 ID를 동시에 보내면 422다. 기존 수유를 사건에 연결할 때 일일 수유가 두 번 집계되지 않는다. 수면은 아기당 진행 중 하나, 감지는 활성 세션 하나를 DB에서 보장한다. 비슷한 시각의 두 보호자 입력은 중복 가능성만 알리고 자동 병합하지 않는다.

## 8 HTTP 오류와 중복 방지

모든 FastAPI 오류는 `code`, `message`, `retryable`, `request_id`, `field_errors`, `details` 형식이다. FastAPI의 기본 입력 검증 오류도 이 형태로 변환한다. A는 message 문자열이 아니라 code로 분기한다. 성공 응답은 각 리소스 스키마를 그대로 반환하며 HTTP request_id는 `X-Request-ID`에도 싣는다.

| HTTP            | code 예시                                                   | A의 처리                                                       |
| --------------- | ----------------------------------------------------------- | -------------------------------------------------------------- |
| 401             | AUTH_REQUIRED, TOKEN_EXPIRED                                | 세션 갱신 1회, 실패하면 재로그인. 다른 계정에 초안 재전송 금지 |
| 403             | OWNER_ONLY, INVITE_EMAIL_MISMATCH, CONSENT_REQUIRED         | 필요한 권한·계정·동의 경로 안내, 무한 재시도 금지              |
| 404             | RESOURCE_NOT_FOUND                                          | 존재하지 않음 또는 접근할 수 없음. 비구성원·타인 초안 포함     |
| 409             | VERSION_CONFLICT, SOURCE_REVISION_CHANGED                   | 최신 값과 사용자 초안 비교, 조용한 덮어쓰기 금지               |
| 409             | ANALYSIS_IN_PROGRESS, NORMALIZATION_IN_PROGRESS             | 기존 ID·조회 경로로 이동                                       |
| 409             | IDEMPOTENCY_KEY_REUSED                                      | 같은 키의 다른 본문. 수정된 작업은 새 키 사용                  |
| 409             | RESOURCE_DELETING                                           | 삭제 진행 화면, 신규 쓰기·재생·분석 차단                       |
| 409             | OWNER_REQUIRED, ACTIVE_SESSION_EXISTS, SLEEP_ALREADY_ACTIVE | 전체 삭제 경로 또는 기존 세션·수면 처리 선택                   |
| 410             | INVITE_EXPIRED, INVITE_REVOKED, RESOURCE_DELETED            | 재초대 또는 삭제 완료 안내                                     |
| 413 / 415 / 422 | FILE_TOO_LARGE / UNSUPPORTED_MEDIA_TYPE / VALIDATION_ERROR  | 파일 교체 또는 해당 필드 수정                                  |
| 429             | RATE_LIMITED                                                | Retry-After 이후 사용자에게 재시도 제공                        |
| 500 / 503       | INTERNAL_ERROR / MODEL_NOT_READY, SERVICE_UNAVAILABLE       | 저장·등록 여부 확인 후 복구, 목 결과로 대체 금지               |

같은 키와 같은 요청이 이미 완료되면 기존 성공·리소스 ID를 반환한다. 단순 재전송 자체를 409 오류로 만들지 않는다. 동일 작업이 실행 중일 때만 기존 작업 ID를 포함한 409를 반환한다. 권한·삭제 검사는 재전송 응답을 반환하기 전에도 수행한다.

모든 변경 요청은 UUID `Idempotency-Key` 헤더를 요구한다. 본문이 있는 변경 요청에는 같은 값의 `client_request_id`를 넣는다. DELETE는 헤더와 version 쿼리를 사용해 본문을 요구하지 않는다. 키 범위는 `(인증 사용자, HTTP 메서드, 대상 경로, 키)`이며 B가 정규화한 본문 해시를 비교한다. 동시에 도착한 요청도 원자적 유일성 검사로 한 번만 처리한다.

최소 7일 동안 중복 방지를 보장한다. A는 미확정 요청을 새 키로 자동 재전송하지 않는다. 새 키는 사용자가 수정한 새 작업 또는 명시적 새 시도에만 발급한다. 중복 방지 저장소에는 가능한 한 요청 해시와 리소스 참조를 보관하고 민감한 원문·전체 응답을 복사하지 않는다. 삭제된 내용이 재전송 캐시로 부활하지 않게 한다.

## 9 브라우저와 FastAPI의 경계

P0의 업무 데이터 조회·생성·수정·삭제는 FastAPI로 통일한다. A에게 허용할 브라우저 Data API 테이블·RPC 목록은 빈 목록으로 확정한다. 두 체크리스트의 “RLS로 허용된 데이터”는 허용 범위의 상한이며 직접 테이블 조회를 필수로 하자는 뜻으로 적용하지 않는다. 이 결정으로 401·403·404·409와 트랜잭션·중복 방지 규칙을 한 계약에서 처리한다.

| 직접 연결         | 허용 범위                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------- |
| Supabase Auth     | 이메일 OTP, 로그인·토큰 갱신·로그아웃                                                    |
| Supabase Storage  | FastAPI가 등록한 업로드 세션의 정확한 private 경로에 인증 업로드, 발급된 단기 URL의 재생 |
| Supabase Realtime | 현재 ACTIVE 멤버십이 허용한 비공개 채널의 최소 변경 신호 구독                            |
| Supabase Data API | P0 업무 테이블 조회·쓰기·RPC 직접 호출 금지                                              |

FastAPI가 맡는 동작은 아기 생성·프로필·멤버십·초대·동의, 생활 기록의 모든 쓰기와 조회, 음원 등록·검증·재생 경로 발급, 분석·LLM·확인 저장, 삭제와 내부 검수·내보내기다. 파일 바이트는 FastAPI나 Vercel을 통과시키지 않고 Storage로 직접 전송한다.

프런트엔드에는 Supabase URL·publishable key·FastAPI 공개 주소만 둔다. 로그인 사용자의 access token으로 인증한다. publishable key는 사용자 토큰을 대체하지 않는다. secret key와 legacy service_role, LLM 키, DB 자격증명은 B의 서버 비밀 저장소에만 둔다. 프런트엔드 저장소·번들·공개 환경 변수에 넣지 않는다.

DB의 업무 테이블은 anon·authenticated에 불필요한 grants를 주지 않고 RLS를 적용한다. 서버 관리자 연결은 RLS를 우회할 수 있으므로 애플리케이션에서 매번 같은 권한 검사를 한다. Storage 정책은 활성 멤버십·ACTIVE 아기·미만료 업로드 세션·업로더·정확한 object_key를 확인한다. 범용 임의 경로 업로드·덮어쓰기·클라이언트 삭제는 허용하지 않는다. 기본 인증 업로드를 사용하므로 멤버십 제거 뒤의 오래된 업로드 시도도 정책으로 차단한다.

Storage·Realtime 정책이 비공개 업무 테이블의 권한을 확인할 때는 B가 API에 노출하지 않는 최소 권한 검사용 함수를 둔다. 이 함수는 현재 인증 사용자만 판정하고 고정 search_path와 필요한 실행 권한만 사용한다. 정책 내부 검사를 가능하게 하려고 브라우저에 업무 테이블 조회 권한을 열지 않는다.

업로드 세션 수명은 15분, 최대 60초·25MB로 정한다. 6MB를 넘거나 연결이 불안정하면 TUS 재개 업로드를 사용한다. 재개는 같은 음원과 경로를 사용하며 만료 후에는 같은 미완료 음원에 새 업로드 세션을 발급한다. 완료 API가 실제 바이트·형식·길이·체크섬과 권한을 다시 검사한 후 READY로 만든다. 서버가 외부 사용자 URL을 다운로드하는 API는 제공하지 않는다.

업로드 취소는 A가 전송을 중단하고 B가 해당 승인을 취소해 임시 객체를 정리한다. 이미 취소한 음원을 다시 전송하려면 현재 화면의 원음이 남아 있는 경우에만 새 audio_id로 시작한다. 검증 응답의 quality_reasons는 길이 부족·무음·잘림·잡음·비울음·디코딩 문제를 구분하며, “시각 불명”은 음원 품질 오류와 별도로 현재 맥락 결합을 제한한다.

Realtime에는 baby_id·revision·변경 ID만 보내고 원문·오디오·분석 결과를 보내지 않는다. A는 신호를 받으면 FastAPI로 재조회한다. 전경에서 5초 간격의 changes 조회를 복구 경로로 두고 창 복귀 때도 재검사한다. 비공개 채널 권한이 토큰 수명 동안 남는 구현에서도 제거된 사용자에게 신규 신호를 보내지 않도록 B가 현재 수신 대상을 검사해 전송한다. A의 구독 해제만으로 권한을 보장하지 않는다.

## 10 동의와 삭제

아기 설정은 SERVICE_PROCESSING, AUDIO_RETENTION, BABY_TRAINING으로 분리하고 개인별 CONTRIBUTOR_TRAINING과 SHARED_USE 수락 이력을 따로 저장한다. 선택 보관과 두 종류 학습 참여는 기본 꺼짐이다. 서비스 처리와 공동 사용 안내에는 외부 LLM으로 정리 대상 텍스트가 전송될 수 있음을 포함한다. 브라우저 마이크 권한은 이 동의와 별개다.

공통 학습에는 아기 학습 설정과 포함된 음원·원문·행동·관찰·수정·확인 기여자의 동의가 모두 필요하다. OWNER가 다른 구성원의 개인 학습 참여를 켜지 못한다. 탈퇴 후에도 본인의 철회는 허용한다. 철회는 신규 학습 내보내기를 즉시 막고 관련 후보·묶음·사본·특징값의 정리를 시작한다. 기존 배포 모델이 즉시 되돌아간다고 표시하지 않는다.

음원 보관을 선택하지 않으면 분석 종료 직후 삭제하며 장애 시 수신 후 최대 1시간 안에 정리한다. 보관 선택은 기본 7일, 적격 학습용 사본은 별도 권한으로 기본 30일이다. 모두 v2의 초기 운영값이다. 외부 제공자·백업의 실제 보관 기간은 이 값으로 확인됐다고 주장하지 않는다.

전체 삭제는 OWNER의 확인 화면을 거쳐 `DELETE /v1/babies/{baby_id}/data`를 호출한다. 원자적으로 Baby=DELETING과 DeletionJob=PENDING을 저장하고 202를 반환한다. 신규 읽기·쓰기·분석·재생 발급을 차단하되 삭제 신청자는 작업 상태를 조회한다. 삭제 도중 끝난 모델·LLM 작업이 결과를 되살리지 못하도록 저장 직전에도 삭제 상태를 확인한다.

삭제는 음원·원문·생활 기록·관찰·라벨·맥락·분석·추천·개인화·학습 사본·특징을 정리한다. 일부 실패하면 job=FAILED와 실패 범위를 표시하고 접근 차단을 유지한다. 사용자에게는 “일부 자료 정리 중”으로 보여주며 삭제 완료라고 표시하지 않는다. 같은 job에 대한 서버 재시도 또는 요청자 재시도를 지원한다.

개별 생활 기록 삭제는 해당 기록과 파생 연결을 DELETING으로 제외하고 아기 전체를 잠그지 않는다. 정상 수정에서 불변인 과거 스냅샷도 삭제 요구에는 해당 내용을 제거하며 `reproduction_status=SOURCE_DELETED`만 남긴다. 본인 기여자료 일괄 삭제는 탈퇴와 별개 endpoint로 제공하고 타인의 독립 기록은 유지한다. 삭제 완료는 설정한 실제 삭제 범위를 모두 확인한 후에만 반환한다.

## 11 목과 출처

`inference_mode=REAL|STUB`는 오디오 실행 구현을, `data_origin=USER|DEMO`는 입력 출처를 나타낸다. 서로 다른 필드로 저장한다. `inference_executed`는 실제 모델 호출 여부다. REAL 설정이더라도 모델 실행 전 실패했으면 실행 완료로 표시하지 않는다. LLM 정규화에도 execution_mode와 사용한 provider·model·prompt·schema·ontology 버전을 별도로 기록한다.

| 조합                        | 사용자 표시                                                        |
| --------------------------- | ------------------------------------------------------------------ |
| REAL + USER, 실제 실행 완료 | 실제 입력 분석                                                     |
| REAL + DEMO, 실제 실행 완료 | 예시 음원 실제 분석                                                |
| STUB + USER 또는 DEMO       | 개발용 고정 응답                                                   |
| 실행 전 실패                | 분석 실패 또는 입력 검사 유보, 실제 모델 실행 완료로 표시하지 않음 |

가상 기록은 DEMO, 개발용 응답은 STUB을 유지한다. 이 폴더의 [목 응답·시험 사용자 배치](./목%20응답과%20시험%20사용자%20배치.json)는 모두 가상 데이터이며 실행 증거가 아니다. 샘플 음원 파일 자체는 포함하지 않는다. 허가된 파일을 붙일 때 B가 원출처·이용 조건·파일 체크섬을 별도 목록에 등록한다. 모델 성능·학습 자료·실사용 요약에 STUB이나 DEMO를 섞지 않는다.

목의 상태값·필드·오류는 [OpenAPI 계약](./openapi계약.json)과 같아야 한다. B는 샘플을 제공하고 A는 같은 API 클라이언트를 목과 서버에 연결한다. 목 사용은 개발 환경 설정으로만 켜며 장애 발생 시 자동으로 실제 분석을 목 응답으로 바꾸지 않는다. 실제 API 전환은 환경 주소와 목 활성 설정만 바꾸는 것을 목표로 한다.

## 12 시험 사용자와 인수 조건

| 시험 사용자 별칭 | 초기 조건                                | 시험 목적                     |
| ---------------- | ---------------------------------------- | ----------------------------- |
| owner_a          | baby_a OWNER, baby_b CAREGIVER           | 관리 권한, 다른 아기로 전환   |
| caregiver_a      | baby_a CAREGIVER                         | 공동 입력, 타인 수정·관리 403 |
| owner_b          | baby_b OWNER, baby_a 비구성원            | 아기 간 격리·404              |
| invited_a        | 초대 대상, 아직 멤버십 없음              | 정상 수락·이메일 불일치·만료  |
| removed_a        | baby_a REVOKED, 과거 기여·동의 이력 보유 | 권한 회수와 탈퇴 후 철회·삭제 |

이 별칭과 가상 UUID는 [목 응답·시험 사용자 배치](./목%20응답과%20시험%20사용자%20배치.json)에 고정한다. 실제 계정은 B가 팀에서 소유한 수신 가능한 이메일로 개발 Supabase에 생성하고 A에게 역할·아기 배치표와 로그인 방법을 전달한다. 공용 비밀번호를 문서에 넣지 않는다. 이번 파일에는 실제 계정 자격증명이나 살아 있는 세션 토큰이 없다.

첫 연동 완료 조건은 아래를 두 계정으로 재현하고 기록하는 것이다. 기능 전체의 P0 완료는 v2 AC01~AC44를 유지한다.

- 초대 정상 수락·만료·재사용·이메일 불일치와 OWNER 자기 탈퇴 차단.
- 아기 전환 중 이전 분석 완료·업로드·미저장 초안이 다른 아기 화면에 섞이지 않음.
- 타인 초안과 비구성원 접근 404, 참여 중 관리 권한 부족 403, 만료 세션 401 구분.
- RUNNING·COMPLETE·ABSTAIN·FAILED 및 요청 미등록·응답 유실·서버 중단 복구.
- 같은 요청 재전송과 동시 전송에서 한 번만 저장, 같은 키의 다른 본문 409.
- 동시 수정 409와 최신 값·로컬 초안 비교, 진행 중 수면과 감지 세션 유일성.
- 자연어 계획·부정·불명확 시각·충돌·LLM 실패·오래된 결과·이중 확인 저장.
- 보관 미동의 분석, 개인 학습 미동의, 탈퇴 후 철회, 삭제 실패 후 접근 차단 유지.
- 기존 기록을 사건 행동에 연결해도 집계가 중복되지 않음.
- 전체 삭제 중 늦은 분석·LLM 응답이 데이터를 복구하지 않음.
- Storage 임의 경로·덮어쓰기·권한 해제 뒤 업로드 거절, 신규 재생 URL 차단.
- REAL·STUB과 USER·DEMO의 두 출처 축이 화면·이력·내보내기에서 보존됨.

B 번호는 A 담당 문서가 명시한 선행 작업의 표기를 사용한다. 이번 문서는 그 작업들이 이미 구현됐다고 판단하지 않는다.

상태 그래픽 자산과 동작 줄이기·대체 텍스트는 A가 구현한다. B는 확인된 관찰의 `state_codes`, `visual_state_code`, `visual_mapping_version`, 관찰 시각·작성자·출처를 반환한다. UNKNOWN 또는 같은 시각의 배타적 상태는 NEUTRAL로 표현하고, 자연어 초안은 확인 전 미리보기로만 보여준다. 홈에는 마지막 확인 상태만 노출하며 30분이 넘으면 정지 그림과 경과시간을 강조한다. 후보 점수로 표정을 선택하지 않는다.

오늘 요약은 아기 시간대의 날짜별 계산값을 B가 반환한다. 수면은 원본 기록 한 개를 유지하며 날짜 경계를 나누어 집계한다. 기록 없음, 수유 횟수는 있으나 양 모름, 실제 0을 구분한다. 다른 기기의 아기 시간대와 다르면 서버 현재 설정으로 다시 요청한다. 준비 패턴은 최근 7일·확인한 3일 이상·유효 간격 10개 이상에서만 제안하고, 사분위 범위가 중앙값의 절반을 초과하면 보류한다. 기저귀는 사용자가 정한 확인 간격만 사용한다.

준비 알림은 사용자별 기본 꺼짐이다. 패턴과 근거 기록은 공유하지만 켜기·10분 미루기·이번 끄기·확인 여부는 수신자 개인 값이다. `SCHEDULED → DUE`, 미루면 SNOOZED, 이번 끄기는 DISMISSED, 새 근거 기록이나 유효기간 종료는 EXPIRED다. 시간 복귀 후 지난 알림을 한꺼번에 전달하지 않는다. P0 전달은 활성 화면과 홈 카드이며 화면 밖 푸시는 P1을 유지한다.

`GET /capabilities`에서 B가 실제로 등록한 모델·지원 라벨·입력 형식·브라우저 감지 버전과 시험 통과 기기를 제공한다. A-02의 결과표에 없는 기기를 지원 완료로 표시하지 않는다. 검증 전 `available=false` 또는 STUB 상태로 두며 실제 가중치 파일·버전·지원 범위를 추측해서 채우지 않는다.

## 14 착수 순서

1. B가 이 계약의 모델과 오류 형식을 FastAPI에 반영하고 개발 DB·RLS·Storage·시험 계정을 준비한다. A는 즉시 합성 목 응답으로 로그인·아기 전환·권한별 화면·오류 UI를 구현하고 A-02 기기 시험을 함께 시작한다.
2. 실제 API로 인증 후 아기 생성·초대·공동 기록·409·삭제 상태를 먼저 연결한다.
3. 업로드·분석·유보·실패·응답 유실 복구를 연결한다. 모델이 준비되지 않은 구간은 STUB으로 표시한다.
4. 정규화·확인 저장·행동·반응을 연결하고 두 계정의 다음 안내 반영을 확인한다.
5. 감지·요약·알림·학습 후보 및 내보내기를 v2의 전체 인수 기준까지 확장한다.

첫 통합 시연의 종료 조건은 A 문서에 맞춰 “두 보호자 로그인 → 녹음 → 실제 분석 또는 정직한 유보 → 행동·상태 확인 기록 → 다른 보호자 화면 반영”으로 고정한다. STUB으로 이 흐름을 확인한 것은 개발 연결 확인이고, 실제 분석을 포함한 통합 시연 완료와 구분한다. 활성 감지·요약·학습 후보는 이후 단계에서 채우되 P0 완료 전에는 모두 검증한다.

백엔드 내부 테이블 정규화, 인덱스, 배포 자동화 세부 구현은 B가 이 계약 안에서 결정한다. 배포 모델 ID·가중치·지원 기기·검증 임계값은 측정 없이 이름을 만들어 확정하지 않는다. B가 검증한 레지스트리를 등록하면 A가 동일 응답 구조로 표시한다. UI와 API의 계약 확정을 그 검증 완료와 혼동하지 않는다.
