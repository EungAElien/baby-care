# 아기 울음 번역기 · 해커톤 시제품 설계안

> 이전 버전 보관본입니다. 현재 제품·API 기준은 [문서 안내](../../README.md)의 v2 문서와 계약을 따릅니다. 본문은 당시 기획을 보존하며 현재 구현 상태를 뜻하지 않습니다.

작성일: 2026-09-15\
상태: 개발 범위와 검증 방법을 제안한 설계 문서. 서비스 코드·모델 학습·실사용 검증은 이 문서 작성에 포함하지 않았다.\
목표: 첫 시제품을 만들어 해커톤에 출품한다. 인원과 마감일은 아직 정해진 정보가 없다.

## 1. 제품 정의와 이번 완료 범위

**아기의 울음과 생활 기록을 함께 살펴 가능한 욕구와 다음 확인 행동을 안내하고, 보호자의 행동과 아기 반응을 기억하는 개인화 육아 도우미.**

첫 시제품의 완성 단위는 다음 순환이다.

**울음 감지 → 울음 분석 → 생활 맥락 확인 → 원인 후보·확인 행동 안내 → 실제 행동·반응 기록 → 다음 안내에 기록 반영.**

‘번역’은 사용자에게 익숙한 기능 이름으로 쓰되 결과는 원인 후보로 표현한다. ‘기록에 반영된다’, ‘모델이 재학습됐다’, ‘정확도가 향상됐다’는 서로 다른 상태다. 정확도 향상은 비교 평가를 통과했을 때만 주장한다.

### 범위 결정

| 구분 | 기능 | 이번 판단 |
|---|---|---|
| P0 필수 | 직접 녹음·파일 입력, 울음/비울음 구별, 녹음 품질 검사 | 실제로 동작하게 구현 |
| P0 필수 | 사용자가 켜둔 화면에서 울음 감지 세션 | 연속 울음을 하나의 사건으로 묶고 중단 상태 표시 |
| P0 필수 | 울음 원인 후보 + 생활 맥락 + 확인 행동 | 지원하는 후보만 표시하고 판단 유보 지원 |
| P0 필수 | 수유·수면·기저귀·달래기 기록과 결과 확인 | 울음과 무관한 평소 기록도 허용 |
| P0 필수 | 아기별 최근 기록·유사 사례 반영 | 작은 기록 조회·집계부터 구현 |
| P0 필수 | 오늘의 요약·기록 기반 돌봄 시점 안내 | 충분한 기록이 없으면 안내 유보 |
| P0 필수 | 데이터 출처·버전·동의·삭제, 평가 결과 | 실제 분석과 데모 데이터를 구분 |
| P1 여유 시 | 음성으로 기록 초안 입력, 다른 보호자와 공유 | 저장 전 확인, 가족별 권한 필요 |
| P1 연구 | 울음 전 예측 모델의 비공개 평가 | 관측 데이터가 있을 때만 실험 |
| P2 확장 | 네이티브 앱·카메라·환경 센서·가전 제어 | 교체 가능한 연결 구조만 먼저 설계 |

사용자 경험은 수유·수면·기저귀 돌봄이 많은 영아 보호자를 우선 대상으로 한다. 기획상 생후 0~6개월을 첫 대상 후보로 두되, 실제 모델의 지원 월령은 학습·평가 데이터가 뒷받침하는 범위로 별도 표시한다. 신생아 데이터로 6개월 전체 성능을 보장하지 않는다.

## 2. 실제 사용 흐름

### 2.1 최초 설정

- 아기 별칭, 생년월일, 수유 방식, 시간대를 입력한다. 필요한 정보부터 받고 병력 등 민감한 항목을 일괄 요구하지 않는다.
- 현재 선택한 아기 1명을 기준으로 녹음한다. 여러 아기나 TV 속 울음을 자동으로 구분할 수 있다고 가정하지 않는다.
- 마이크 이용, 녹음 저장, 공통 모델 개선 참여를 각각 구분한다. 공통 학습에 동의하지 않아도 기록과 분석 기능은 사용할 수 있게 설계한다.
- 개인화에 쓸 기록이 없으면 ‘아직 참고할 기록이 적어요’를 표시한다.

### 2.2 감지와 녹음

- ‘지금 분석’은 짧게 녹음한다. 10~20초는 초기 사용성 실험용 길이이며 의료적·모델 성능 기준이 아니다. 충분한 입력 확보 여부에 따라 종료하거나 추가 녹음을 요청한다. 녹음을 위해 돌봄을 늦추도록 요구하지 않는다.
- ‘감지 시작’은 페이지를 켜둔 동안 주변 소리를 처리하고 울음 후보 구간을 발견한다. 소리 크기나 일반 음성 감지만으로 울음이라고 확정하지 않는다.
- 울음 감지용 모델은 울음과 함께 성인 말소리, TV, 웃음, 생활 소음, 조용한 구간을 구별하도록 평가한다. 원인 분류용 울음 자료만으로 이 기능을 검증할 수 없다.
- 이어지는 울음은 사건 하나로 묶고 알림이 반복되지 않도록 한다. 사건 시작·종료 조건은 실제 녹음으로 조정하는 설정값으로 둔다.
- 잡음, 소리 잘림, 입력 부족, 마이크 권한 거부, 네트워크 장애를 구분한다. 판정 불가를 임의의 원인으로 대체하지 않는다.
- 원시 주변 소리를 계속 서버에 보관하는 구조는 피하고, 분석에 필요한 구간 중심으로 처리한다. 일시 버퍼와 업로드 구간도 사용자에게 설명한다.

웹의 첫 지원 범위는 ‘화면을 켜고 사용자가 실행한 세션’이다. 페이지 비활성화·마이크 트랙 종료·연결 손실 시 감지가 멈췄음을 기록하고 재개를 안내한다. 화면 잠금 후 24시간 감지는 첫 버전의 완료 기준에 넣지 않는다. 브라우저가 숨겨진 페이지를 정지하거나 폐기할 수 있다는 점을 고려한 범위 결정이다. [Chrome Page Lifecycle 문서](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

### 2.3 분석 결과

결과 화면은 세 부분으로 나눈다.

1. **원인 후보:** 배고픔·졸림·불편함 중 현재 모델이 지원하는 후보. 필요하면 ‘원인을 좁히기 어려워요’.
2. **참고한 정보:** 오디오 분석, 마지막으로 기록된 수유·수면·기저귀, 보호자 관찰, 이전 유사 사례. 근거마다 출처를 표시한다.
3. **지금 확인할 행동:** 한 번에 우선 행동 1개와 다른 선택지 1~2개. ‘확인했어요’, ‘다른 행동을 했어요’, ‘기록이 잘못됐어요’ 제공.

예시 화면 문구 — 실제 분석 결과가 아닌 설계 예시:

> 수유 필요 여부를 먼저 확인해 보세요.\
> 마지막으로 기록된 수유와 시간이 떨어져 있고, 이전에 비슷한 상황에서 수유 뒤 진정되었다는 기록이 있어요.\
> 최근 수유 기록이 빠졌다면 알려주세요. 기저귀나 졸림 신호도 함께 살펴볼 수 있어요.

원인 후보와 돌봄 행동은 일대일로 묶지 않는다. ‘기저귀 확인’은 중요한 돌봄 행동이지만 공개 울음 라벨만으로 별도의 ‘기저귀 울음’을 학습했다고 주장할 수 없다. 복통·통증 라벨이 있는 데이터도 의료적 진단 결과로 그대로 노출하지 않는다.

초기에는 모델 내부 점수를 ‘배고픔 87%’처럼 현실 확률로 보여주지 않는다. 필요하다면 후보의 순서와 판단 유보를 사용하고, 검증 자료에서 점수와 실제 발생 비율의 관계를 확인한 후 확률 표시 여부를 결정한다. 판정 불가 사유는 ‘잡음’, ‘기록 부족’, ‘후보를 좁히기 어려움’ 등으로 구분한다.

### 2.4 기록과 반응

보호자가 실제 행동을 하고 나서 빠르게 기록한다. 수유·수면·기저귀 버튼과 최근 시각을 기본값으로 제공하고 상세 입력은 선택으로 둔다.

| 기록 종류 | 필수·핵심 정보 | 선택 정보 |
|---|---|---|
| 수유 | 시각, 방식 | 분유량·유축유량, 모유 수유 시간; 모르는 양은 빈값 |
| 수면 | 잠든 시각·깬 시각 또는 진행 중 | 잠들기 어려움 메모 |
| 기저귀 | 확인/교체 시각 | 젖음·대변·깨끗함·확인 못함 |
| 달래기 | 안기·트림 돕기·환경 조절 등과 시각 | 자유 메모 |
| 아기 반응 | 진정됨·일부 진정·변화 없음·다시 욺·확인 못함 | 관찰 시각, 진정까지 걸린 시간 |
| 보호자 해석 | 배고팠던 것 같음·졸린 것 같음·복합·모름 | 해석 확신 정도 |

- 하나의 울음 사건에 여러 행동을 순서대로 연결한다. ‘안기 → 수유 → 기저귀 교체’에서 마지막 행동만 정답으로 만들지 않는다.
- 반응을 확인하지 않았으면 미확인이다. 미응답을 성공이나 실패로 바꾸지 않는다.
- 울음이 없었던 평소 수유·수면·기저귀도 같은 입력 방식으로 남길 수 있다.
- 늦게 입력하거나 수정할 수 있게 하고, 실제 발생 시각과 입력 시각을 각각 보관한다.
- 기록 후 바로 확인을 강제하지 않는다. 다음 앱 진입 시 짧은 반응 확인을 제공할 수 있다.

### 2.5 평소 육아 도움

- 오늘 수유·수면·기저귀의 최근 기록과 진행 중인 수면을 한 화면에 보여준다.
- ‘오늘 총수면’은 누락된 구간이 있으면 ‘기록된 수면 합계’로 표현한다.
- 최근 기록의 대표 간격과 변동 폭을 보여주고, ‘평소 기록상 확인할 시점이 가까워요’와 같은 준비 알림을 제공한다.
- 통계는 기록 기간·건수·누락 가능성과 함께 표시한다. 적은 기록에는 알림을 보류한다. 최소 건수는 사용성·자료 검증을 위한 운영 설정이지 예측 신뢰성을 보장하는 과학적 기준이 아니다.
- 기록 간격은 아기의 현재 욕구를 확인할 단서다. 시간표에 맞춰 강제로 먹이거나 재우라는 지시로 사용하지 않는다.
- 자유 질문 챗봇은 P1로 미룬다. 먼저 최근 기록을 정확하게 요약하는 기능을 완성한다.

## 3. 개인화와 학습 구조

### 3.1 세 가지 개선을 분리한다

| 단계 | 구현 | 사용자에게 설명할 수 있는 것 |
|---|---|---|
| 즉시 기록 반영 | 최근 수유·수면 등이 수정되면 맥락과 행동 안내 재계산 | ‘방금 수정한 기록을 반영했어요’ |
| 아기별 개인화 | 유사한 이전 상황과 행동·반응 조회, 최근성·기록 품질 고려 | ‘이 아기의 이전 기록을 참고했어요’ |
| 공통 모델 개선 | 동의받은 자료 정리 → 학습 → 별도 평가 → 새 버전 배포 | 평가 근거가 있을 때 ‘새 모델이 이 평가에서 개선됐어요’ |

첫 시제품은 첫 두 가지를 실제 구현한다. 모델 가중치를 매 클릭마다 수정하지 않는다. 전체 모델의 학습·평가·버전 관리 절차도 개발 산출물에 포함하되, 새로운 실사용 자료가 충분하지 않으면 개선 성과를 만들어내지 않는다.

### 3.2 초기 개인화의 구체적 계산

1. 분석 시점에 알려져 있던 생활 기록을 조회한다. ‘마지막 기록 후 경과시간’과 기록 유무·최근성을 구분한다.
2. 해당 아기의 이전 사건 중 월령 변화, 시간대, 수유·수면 경과, 입력 품질이 비슷한 사례를 찾는다. 선택적으로 울음 임베딩의 유사도를 추가한다.
3. 어떤 행동을 했고 어떤 반응을 관찰했는지 표본 수와 함께 요약한다. 복합 행동·결과 미확인은 별도 취급한다.
4. 오디오 결과와 맥락이 충돌하면 중요한 누락 관찰을 최대 1~2개 질문한다. 답하지 않아도 판정 유보 또는 넓은 확인 목록으로 진행한다.
5. 기록이 적으면 오디오 후보와 일반 확인 목록으로 돌아간다. 억지로 개인화 문장을 만들지 않는다.

첫 버전에서 맥락 결합은 명시한 규칙과 과거 사례 조회로 구현해도 된다. 이 경우 ‘맥락 모델을 학습했다’고 표현하지 않는다. 같은 사건에 연결된 오디오·과거 맥락·반응이 쌓이면, 작은 분류기나 순위 모델이 각 입력을 얼마나 참고할지 학습하도록 발전시킨다. 서로 다른 공개 데이터의 오디오와 임의의 육아 기록을 합성해 실제 결합 학습 데이터인 것처럼 쓰지 않는다.

### 3.3 관찰과 정답의 차이

**수유 후 진정됨은 수유가 도움이 된 관찰이지, 울음 원인이 배고픔이었다는 확정 정답이 아니다.**

안아 준 효과, 자연 진정, 앞선 행동, 여러 욕구가 함께 작용할 수 있다. 따라서 아래 항목을 분리한다.

- 모델 추정
- 보호자가 했다고 기록한 행동
- 관찰된 반응
- 보호자의 원인 해석
- 실제 학습에 포함할지에 대한 검수 상태

일반적인 경우 음향 라벨은 ‘보호자 보고 원인’ 또는 ‘행동·반응에서 얻은 불완전한 단서’라고 정의한다. 원인 정답과 행동 효과를 같은 목표로 학습하지 않는다. 추천받아서 실행한 행동은 추천 영향도 기록한다. 모델이 자신의 추천을 사실로 다시 학습하는 오류를 막기 위한 구분이다.

### 3.4 오디오 모델 개발 순서

1. **기준 모델:** Dasheng-Base 같은 사전학습 오디오 Transformer를 고정하고 작은 울음 분류기를 학습한다. 이전 대화의 M1 환경에서 먼저 작은 실험을 하는 구성이다. 실제 속도·메모리는 대상 입력으로 측정한다. [Dasheng 공식 저장소](https://github.com/XiaoMi/dasheng)
2. **원인 분류 실험:** 사용 권한을 확인한 라벨 자료로 실험한다. 원본 라벨, 제품 후보로의 매핑, 지원하지 않는 라벨을 버전 관리한다.
3. **특징 추가 실험:** 음높이 변동·울음 길이·불규칙성 등 기존 연구의 특징을 보조 입력으로 추가하고, 없는 모델보다 나은지 비교한다. 연구 집단의 평균값을 진단 기준으로 쓰지 않는다.
4. **여유가 생기면:** 일부 층 추가 학습 또는 M2D 기반 울음 자기지도 추가 학습을 비교한다. 대량 추가 학습은 시제품 완성의 선행 조건으로 두지 않는다. [M2D 공식 저장소](https://github.com/nttcslab/m2d)

## 4. 울기 전 예측 — 이번 구현 가능성

### 4.1 이번에는 어디까지 가능한가

| 수준 | 출력 예 | 필요 조건 | 첫 시제품 결정 |
|---|---|---|---|
| 기록 기반 준비 안내 | ‘최근 기록상 수면 준비를 확인할 시점이 가까워요’ | 평소 기록과 간단한 통계 | 구현 권장 |
| 울음 발생 확률 | ‘앞으로 30분 안에 울음이 시작할 확률’ | 울음·비울음 시간대가 연결된 연속 관측 | 데이터가 있을 때 연구용 비공개 평가 |
| 예방 행동의 효과 | ‘지금 이 행동을 하면 울음이나 불편이 줄어든다’ | 행동 선택의 영향까지 평가할 연구 설계 | 후속 확장 |

30분은 예측 문제를 구체화하기 위한 예시 시간 범위다. 실제 제품 범위는 데이터와 활용 방식에 맞춰 정한다.

### 4.2 울음 파일만으로는 해결되지 않는 이유

다음 두 질문은 다르다.

- 이미 우는 중일 때 무엇을 확인할지: 현재 울음 + 과거 맥락으로 판단.
- 아직 울지 않을 때 앞으로 울지: **현재까지의 정보와 이후 울음 시작 여부**가 모두 기록되어야 판단 가능.

울음이 생겼을 때만 수집한 파일은 울지 않았던 조건을 충분히 알려주지 않는다. 기존 공개 울음 자료만으로 개인의 하루 예측 모델을 완성할 수 없다.

확장을 위해 필요한 자료는 `관측한 시간대 + 센서가 정상인지 + 울음 시작·종료 + 수유·수면 등 사건 + 사전 안내와 실제 행동`이다. 센서가 꺼져 있거나 아기가 다른 곳에 있던 구간은 ‘안 울었음’으로 채우지 않는다.

### 4.3 예측 학습 설계

- 입력 시점에는 아직 울음이 진행 중이지 않아야 한다. 이미 시작한 울음 감지를 사전 예측 성과로 세지 않는다.
- 입력은 그 시점에 이용 가능했던 기록만 사용한다. 나중에 입력된 과거 수유 기록도 당시 입력에는 없었던 것으로 처리한다.
- 예측 범위 전체를 관측했고 울음이 없을 때만 음성 사례(발생하지 않음)로 둔다. 중간에 관측이 끊겼다면 결과 미확인으로 처리한다.
- 시간대별 빈도·마지막 사건 후 경과시간 같은 단순 기준과 작은 예측 모델부터 비교한다. 복잡한 시계열 Transformer는 추가 성능이 확인되면 검토한다.
- 과거 기간으로 학습하고 미래 기간으로 평가한다. 서로 겹치는 예측 구간이 경계 양쪽에 섞이지 않도록 한다.
- 예측 범위, 관측률, 놓친 울음, 하루 불필요 알림, 미리 알린 시간, 확률의 보정 상태를 함께 평가한다.
- 아직 검증되지 않은 예측은 보호자에게 노출하지 않고 결과만 저장하는 평가 모드로 둔다. 녹음·자료 수집 자체는 동의를 받아야 한다.

### 4.4 확률과 예방 효과는 별도다

‘울 가능성이 높다’를 맞혀도 ‘수유를 하면 예방된다’는 결론이 나오지 않는다. 사전 추천으로 보호자 행동이 바뀌면 이후 울음도 달라져 예측 평가가 영향을 받는다. 추천 여부·모델 버전·실행 행동을 함께 기록한다.

실행하지 않은 다른 행동의 효과는 현재 기록만으로 관찰할 수 없다. 후속 효과 검증은 전문가와 관찰 연구·적절한 비교 설계를 정한 뒤 진행한다. 돌봄을 미루거나 일부러 울게 만들며 실험하지 않는다. 목표는 필요한 돌봄을 제때 돕고 보호자 부담을 줄이는 것이다.

## 6. 개발 구조

### 6.1 권장 구성

소규모 팀을 위한 선택안은 웹 화면(React/Next.js 등) + Python API/FastAPI + PostgreSQL + 비공개 오디오 저장소다. 모델 추론은 별도 모듈로 두어 브라우저·서버·네이티브·전용 기기 중 실행 위치를 바꿀 수 있게 한다. 이 문서는 특정 버전이나 기존 구현의 존재를 전제하지 않는다.

역할을 나눈다.

- **CaptureProvider:** 마이크·파일·미래의 카메라에서 입력과 관측 품질을 받는다.
- **CryDetector:** 울음 구간을 찾고 사건 시작·종료를 만든다.
- **AudioAnalyzer:** 음향 특징과 지원하는 원인 후보를 만든다.
- **ContextBuilder:** 분석 시점에 알 수 있던 생활 기록과 누락 상태를 묶는다.
- **CareRecommender:** 오디오·맥락·과거 사례에서 확인 행동과 근거를 선택한다.
- **RecordService:** 실제 행동·반응·수정 이력과 아기별 기록을 보관한다.
- **ReminderService:** 평소 기록에서 준비 안내를 만든다. 미래 확률 예측기는 별도 모듈이다.
- **ModelRegistry:** 학습 데이터 목록·모델 버전·평가 결과·활성 모델을 관리한다.
- **DeviceAdapter:** 후속 IoT의 관측과 명령을 공통 형식으로 연결한다.

처음부터 각각 별도 서버로 나눌 필요는 없다. 한 API 안의 모듈로 시작하고, 추론 작업만 필요에 따라 분리한다.

언어 모델을 쓰더라도 역할은 구조화된 결과의 설명과 기록 문장 해석이다. 원인 확률·의료 판단·가전 명령을 자유롭게 생성하게 하지 않는다. 첫 버전 설명은 템플릿만으로도 구현할 수 있다.

### 6.2 핵심 데이터

| 개체 | 보관할 핵심 필드 |
|---|---|
| Baby | baby_id, 보호자 소속, 생년월일/월령 계산 기준, 수유 방식, 시간대 |
| CareEvent | event_id, baby_id, 종류, 실제 발생 시각, 기록 시각, 수정 버전, 입력 출처, 수량·단위, 관련 cry_episode_id(선택) |
| CryEpisode | episode_id, baby_id, 시작·종료, 입력 출처, 감지 결과, 품질, 오디오 보관 참조, 데모 여부 |
| ContextSnapshot | snapshot_id, 분석 시각, 당시 이용 가능했던 event_id와 버전, 누락·경과시간 |
| Analysis | analysis_id, episode_id, snapshot_id, 모델 버전, 후보와 내부 점수, 판단 유보 사유, 실험/활성 상태 |
| Recommendation | recommendation_id, analysis_id 또는 reminder_id, 행동, 근거 사건, 규칙·모델 버전, 노출·선택 여부 |

| Outcome | outcome_id, action_id 또는 episode_id, 관찰 시각, 반응, 보호자 해석, 미확인·복합행동 표시 |
| ObservationWindow | 관측 시작·종료, 마이크·센서 정상 여부, 아기가 관측 범위에 있는지, 감지 버전, 관측 중단 사유 |
| Consent | 보호자, 허용 목적, 버전, 동의·철회 시각 |
| ModelVersion | 학습 자료 목록, 허용 라벨, 지원 범위, 전처리·특징 버전, 평가 결과, 활성화·되돌리기 정보 |

모든 사건은 발생 시각과 기록 시각을 구분한다. ‘기록 없음’은 ‘행동을 하지 않음’과 다르다. 같은 녹음의 파생 구간은 원본 ID를 유지한다.

### 6.3 API 계약 초안

| 동작 | 예시 경로 | 중요한 계약 |
|---|---|---|
| 녹음 등록 | POST /v1/cry-episodes | 아기·시각·입력 출처·중복 방지 키, 허용 형식·길이 확인 |
| 분석 요청 | POST /v1/cry-episodes/{id}/analyses | 분석 시점 맥락을 고정, 작업 ID 반환 |
| 분석 조회 | GET /v1/analyses/{id} | 처리 상태, 후보, 사용 근거, 판단 유보, 버전 |
| 평소 기록 | POST /v1/babies/{id}/care-events | 중복 방지 키, 사건 시각·기록 시각 구분 |
| 기록 수정 | PATCH /v1/care-events/{id} | 예상 버전 확인, 충돌 시 409와 최신 버전 |
| 행동·결과 기록 | POST /v1/cry-episodes/{id}/actions, POST /v1/actions/{id}/outcomes | 복수 행동·미확인 결과 허용 |
| 요약·알림 | GET /v1/babies/{id}/summary, GET /v1/babies/{id}/reminders | 집계 기간, 건수, 누락 상태, 근거 사건 |
| 학습 동의 | PUT /v1/consents | 서비스 분석·보관·공통 학습 동의를 분리 |
| 자료 삭제 | DELETE /v1/babies/{id}/data | 삭제 작업 상태와 범위 확인; 모델 반영 범위 별도 설명 |

분석 상태: 입력 대기 → 품질 검사 → 분석 중 → 결과 / 판단 유보 / 실패. 판단 유보는 정상 분석 결과다. 행동 상태: 안내 → 실제 행동 기록 → 반응 대기 → 반응 기록 / 미확인 종료.

동일 요청을 재시도해도 녹음·수유·행동이 중복 생성되지 않아야 한다. 기록 수정 후 새 안내는 다시 계산하되 기존 분석의 당시 근거는 바꾸지 않는다. 인증된 보호자의 아기만 접근하도록 모든 경로에서 확인한다.

### 6.4 저장·운영

- 데모 자료는 별도 데이터 영역과 표시를 사용하고 실제 학습·평가 집계에서 제외한다.
- 녹음 저장을 끈 사용자는 분석 후 원본을 삭제한다. 보관에 동의한 구간도 목적별 보관 기간과 삭제 기능을 둔다.
- 계정·아기별 접근 권한을 검사하고 오디오를 공개 URL로 노출하지 않는다.
- 학습 참여 철회 시 이후 학습 대상에서 제외하고 아직 사용하지 않은 학습 사본을 정리한다. 이미 학습된 모델에서 영향이 즉시 사라진다고 약속하지 않는다.
- 모델 파일·설정·평가 자료를 버전으로 묶어 이전 버전으로 돌아갈 수 있게 한다. 새 모델 활성화는 평가를 통과한 뒤 별도 절차로 처리한다.
- 실패·지연·판정 유보를 운영에서 구분한다. 로그에 가정 내 대화나 원시 오디오를 무심코 넣지 않는다.

## 7. 네이티브 앱과 IoT 확장

### 7.1 확장 순서

1. **네이티브 앱:** 알림, 빠른 기록, 잠금 화면 연계, 가족 공유, 로컬 추론. 백그라운드 녹음은 운영체제 권한·배터리·중단 동작을 별도 실기기로 검증한다. 네이티브라는 이유만으로 상시 감지를 보장하지 않는다.
2. **카메라·환경 센서:** 보호자 관찰을 보완하는 입력을 추가한다. 장기 감지는 휴대전화 외의 전용 기기·허브에서도 수행할 수 있게 한다.
3. **기기 상태 조회:** 실제 사용 중인 가전의 상태를 맥락에 포함한다.
4. **보호자 확인 후 명령:** 제한된 기기 기능부터 시작한다.
5. **허용한 반복 규칙 자동화:** 지원 기기와 검증된 범위에서만 후속 검토한다.

### 7.2 기기별 구체 기능

| 기기 | 입력·활용 후보 | 제어 범위 제안 |
|---|---|---|
| 요람 주변 카메라·마이크 | 움직임, 눈 개폐가 보이는지, 보호자 접근, 울음 시각 동기화 | 우선 관찰·기록 보조. 수면 추정은 확인 가능한 초안으로 제공 |
| 적외선 야간 카메라 | 어두울 때 움직임·눈·가림 상태 관찰 보조 | 야간 화질과 가림 여부를 품질 정보로 포함 |
| 온습도 센서 | 측정 위치·시각이 있는 실내 온습도 | 오래된 값은 현재값으로 사용하지 않음 |
| TV | 전원·음량 등 지원 상태, 소음 맥락 | 보호자가 확인한 음량 낮추기·음소거 |
| 스피커 | 재생 여부·음량 등 | 보호자가 고른 소리의 재생·중지; 최대 음량·시간 제한 |
| 에어컨 | 현재 설정과 실내 센서 값 | 보호자가 정한 범위 안의 설정 변경; 의료적 온도 처방과 분리 |
| 분유 제조기 | 공식 제공 기능에 한해 준비 상태·완료 상태 | 후순위. 제조 명령은 별도 확인, 기기 인터록·취소·중복 방지 필요 |

일반 야간 적외선 카메라는 근적외선 조명으로 어두운 곳을 보는 방식이며, 온도 측정용 열화상과 다르다. 이를 자동 체온계로 취급하지 않는다. [Axis 기술 설명](https://whitepapers.axis.com/en-us/ir-in-surveillance), [Axis 온도 측정 카메라 설명](https://whitepapers.axis.com/en-us/thermometric-cameras)

영상에서 눈이 감겨 있거나 움직임이 없다는 사실만으로 수면·호흡 정상·건강 상태를 확정하지 않는다. 생체징후 감시와 의료적 경보는 별도 제품·검증 영역이다. FDA도 미검증 영아 생체징후 모니터의 부정확한 측정과 과도한 의존을 지적한다. 이는 미국 자료이며 한국 출시 규제 판단을 대체하지 않는다. [FDA 안전 공지](https://www.fda.gov/medical-devices/safety-communications/do-not-use-unauthorized-infant-devices-monitoring-vital-signs-fda-safety-communication)

### 7.3 연결 계약

모든 관측 입력은 source_id, captured_at, received_at, unit, quality, availability를 가진다. 장치가 꺼지거나 카메라가 가려지면 해당 입력을 제외하고 오디오·생활 기록만으로 계속 동작한다.

기기 연결은 제조사마다 교체 가능한 어댑터를 둔다. 어댑터는 지원 기능 목록, 현재 상태 조회, 명령 제안·실행, 결과 확인을 제공한다. Matter는 연결 후보다. 공식 규격은 Matter 1.5에서 카메라 지원을 추가했지만, 특정 제품의 API·컨트롤러·지역·펌웨어가 실제로 원하는 기능을 제공하는지는 제품별 확인이 필요하다. [CSA 공식 발표](https://csa-iot.org/newsroom/matter-1-5-introduces-cameras-closures-and-enhanced-energy-management-capabilities/)

명령 상태는 제안 → 보호자 확인 → 전송 → 기기 확인 / 실패 / 결과 불명으로 나눈다. 서버가 명령을 보냈다는 사실만으로 실제 동작 완료를 기록하지 않는다. 중복 방지 키, 유효기간, 취소, 상태 재조회, 수동 중지, 명령 이력을 포함한다. 결과 불명인 분유 제조 명령을 자동 재시도하지 않는다.

이번 해커톤에서 가상 기기를 보여주면 ‘가상 기기 데모’라고 표시한다. 실제 연동 완료와 구분한다.

## 8. 검증과 완료 기준

### 8.1 제품 기능의 완료 기준

- 실제 녹음·입력으로 울음 감지와 분석이 실행되고 임의 결과를 반환하지 않는다.
- 비울음·잡음·권한 거부·연결 중단을 처리한다. 감지 실패를 아기가 조용하다는 확인으로 바꾸지 않는다.
- 한 울음 사건의 분석, 근거 기록, 복수 행동, 반응을 끝까지 조회할 수 있다.
- 울음 없이도 평소 돌봄을 기록할 수 있다. 기록 수정·삭제·중복 재시도를 처리한다.
- 수유 기록 등을 수정하면 해당 근거와 다음 행동 안내가 실제로 달라질 수 있다. 변화 이유를 추적할 수 있다.
- 기록이 적을 때 개인화·준비 안내를 유보하고 충분할 때 사용한 기간·사례 수를 보여준다.
- 원시 데이터·합성 시연 자료·모델 추정·보호자 관찰을 구분한다.
- 저장·학습 동의와 아기별 접근 제어가 동작한다.

### 8.2 AI 평가

동일한 평가 사건으로 다음 비교를 한다.

| 비교 | 입력 | 검증 질문 |
|---|---|---|
| A | 생활 기록만 | 오디오 없이 가능한 수준은? |
| B | 울음만 | 울음 자체가 주는 단서는? |
| C | 울음 + 생활 기록 | 맥락 기준 모델에 오디오가 추가 가치를 주나? |
| D | C + 아기별 과거 사례 | 개인화가 미래 사건에서 도움이 되나? |

- 같은 녹음의 조각과 변형 파일을 학습·평가 양쪽에 넣지 않는다.
- 새로운 아기 평가와 같은 아기의 미래 평가를 분리한다. 아기 ID가 불명확한 공개 자료에서는 새 아기 일반화를 검증했다고 주장하지 않는다.
- 클래스별 재현율·Macro F1·혼동 사례, 판단 유보 비율과 유보 후 성능, 소음 조건별 성능을 함께 기록한다.
- 울음 감지는 울음 사건을 찾은 비율, 관측 시간당 오탐, 감지 지연을 별도 평가한다.
- 행동·반응은 기록 완료율, 보호자 입력 부담, 반복된 잘못된 안내 등을 본다. ‘진정됨’만으로 원인 정확도를 평가하지 않는다.
- 자료가 적으면 결과의 범위를 그대로 표시한다. 합성 맥락 데모는 C·D가 실제로 정확해졌다는 근거가 아니다.

수치 목표는 초기 기준 모델과 평가 자료를 확인한 뒤 정한다. 현시점에서 ‘정확도 90%’ 같은 달성 약속을 하지 않는다. 감지·원인 추정·개인화·사전 예측은 서로 다른 성능 항목이다.

### 8.3 안전과 설명의 완료 기준

원인 후보에 졸림이 있더라도 질병을 배제하거나 ‘안전하다’고 표현하지 않는다. 보호자가 호흡 곤란·청색증·깨우기 어려움 같은 심각한 징후를 직접 보고한 경우 일반 돌봄 추천보다 긴급 도움 안내를 우선한다. 이것을 음향 모델이 자동으로 탐지한다고 가정하지 않는다. 구체 안내 문구는 공식 소아 자료에 근거해 관리한다. [NHS 영유아 긴급 도움 안내](https://www.nhs.uk/baby/health/when-to-get-urgent-medical-help-for-babies-and-children-under-5/)

## 9. 개발 순서와 해커톤 시연

| 순서 | 산출물 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 1 | 라벨·이용 조건·중복 자료 점검, 오디오 기준 모델 | 실제 성능과 지원 범위를 확인 |
| 2 | 아기 프로필·평소 기록·울음 사건 저장 | 데이터 연결과 수정·중복 방지 동작 |
| 3 | 녹음·감지·분석·판정 유보 | 실제 입력으로 정상·실패 흐름 동작 |
| 4 | 맥락 기반 확인 행동 + 실제 행동·반응 기록 | 사건 하나의 전체 순환 완성 |
| 5 | 과거 사례 반영 + 오늘 요약·준비 안내 | 기록 수정과 부족 상태 처리 |
| 6 | 비교 평가·발표 자료·재현 가능한 시연 | 실제 구현·실험·확장 계획을 구분 |

해커톤 시연 예시:

1. 사용 권한이 확인된 울음을 입력하고 실제 분석 결과를 보여준다.
2. 생활 기록을 함께 보여주며 왜 특정 확인 행동을 제안했는지 설명한다.
3. ‘방금 수유했는데 기록하지 않았다’를 추가하고 안내가 재계산되는 것을 보여준다.
4. 다른 행동과 반응을 기록해 타임라인에 연결되는 것을 보여준다.
5. 충분한 예시 기록이 있는 프로필에서 과거 사례·준비 안내를 보여준다. 합성 기록은 화면에서 표시한다.
6. 미래 확장은 별도 화면에서 카메라·가전 어댑터와 예측 연구 계획으로 설명한다.

시연에서 즉시 바뀌는 것은 맥락과 사례 조회다. 신경망을 몇 초 만에 재학습해서 정확도가 올랐다고 설명하지 않는다. 실제로 모델이 성능을 내지 못하면 분석·기록 시제품과 연구 결과의 한계를 그대로 제시한다.
