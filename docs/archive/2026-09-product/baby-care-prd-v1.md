# 아기 울음 육아 도우미 PRD

> 이전 버전 보관본입니다. 현재 제품·API 기준은 [문서 안내](../../README.md)의 v2 문서와 계약을 따릅니다. 본문은 당시 기획을 보존하며 현재 구현 상태를 뜻하지 않습니다.

버전 1.1 · 2026년 9월 16일 · 해커톤 첫 시제품 개발 기준

아기의 울음과 생활 기록을 함께 살펴 가능한 욕구와 다음 확인 행동을 안내하고, 보호자의 행동과 아기 반응을 기억하는 개인화 육아 도우미를 만든다. 이번 출시의 완성 단위는 **감지 → 원인 후보 → 맥락에 맞는 확인 행동 → 행동과 상태 및 반응 입력 → 라벨 확인 → 공동양육 기록과 다음 안내에 반영**이다.

이 문서는 제품 목표, 구현 우선순위, 사용자 경험, 검증 및 출시 조건을 정한다. 화면 동작과 데이터 계약은 함께 제공하는 기능명세서가 담당한다. 실제 성능, 사용자 조사 결과, 학습 완료 또는 배포 완료를 보고하는 문서는 아니다.

### 이번 개정에서 추가한 범위

이번 시제품에 선택지와 자연어를 함께 쓰는 행동 및 아기 상태 입력, LLM 정규화와 라벨 확인, 상태별 그래픽, 학습 후보 데이터 구성, 공동양육자 계정 연동을 포함한다. 울음 이외의 옹알이·웃음·칭얼거림과 육아 맥락을 결합한 기분 추론은 후속 확장이다.

## 1 제품 방향과 결정 기준

### 지금 확정된 방향

- 첫 시제품을 해커톤에 출품한다. 반응형 웹앱으로 시작한다.
- 울음 감지와 원인 후보 안내가 핵심 기능이며, 평소 육아 기록과 사건별 행동 및 반응을 연결한다.
- 기록을 다시 활용해 보호자가 다음에 확인할 행동을 더 쉽게 고르게 한다.
- 대응 행동, 관찰한 상태와 반응을 선택지 또는 자연어로 입력하고 LLM 정규화 결과를 보호자가 확인한다.
- 확인된 상태에 맞는 그래픽과 짧은 애니메이션으로 기록 결과를 쉽게 알아보게 한다.
- 엄마, 아빠, 조부모 등 공동양육자가 각자 계정으로 같은 아기의 기록과 맞춤 안내를 공유한다.
- 네이티브 앱, 적외선 카메라를 포함한 관찰 기기, 가전 연동을 후속 확장으로 둔다.
- 오디오 모델의 주 학습 경로는 **사전학습 M2D → BABYCRY 자기지도 추가학습 → Donate-a-Cry 지도학습 → 평가 → 배포**로 한다. 최신 학습 계획을 따른다.

### 이번 문서에서 정한 구현 기본안

P0는 해커톤 완료에 필요한 범위, P1은 핵심 흐름 완성 뒤 추가할 범위, P2는 후속 제품 확장이다. 아기별 관리 보호자 1명과 초대받은 공동양육자를 지원한다. 계정당 직접 생성할 수 있는 아기는 1명이며, 초대받은 아기는 추가로 참여할 수 있다. 한 번에 활성 아기 1명을 선택한다. 로그인 방식, 녹음 길이, 알림 최소 기록 수, 보관 기간 등은 개발을 시작하기 위한 제안값이며 검증된 최적값이나 법적 기준을 뜻하지 않는다.

인원, 마감일, 해커톤 평가 규칙, 공개 대상 수는 아직 정해진 정보가 없다. 따라서 일정은 날짜 대신 단계와 종료 조건으로 제시한다. 제품 책임자가 이 네 가지를 확정하면 같은 범위표에서 우선순위를 조정한다.

## 2 문제와 첫 사용자

### 해결할 문제

보호자는 아기가 울 때 최근 수유, 수면, 기저귀 상태를 떠올리고 여러 행동을 시도한다. 기록 앱과 울음 분석이 분리돼 있으면 이전에 무엇을 했고 어떻게 반응했는지를 현재 판단에 활용하기 어렵다. 이 제품은 울음 분석을 돌봄 기록에 연결해 다음 확인 행동을 고르는 과정을 돕는다.

이는 사용자 구상에 근거한 문제 가설이다. 인터뷰나 실사용 효과가 확인됐다고 가정하지 않는다. 초기 관찰에서 보호자가 실제로 어려워하는 순간과 기록 부담을 먼저 확인한다.

### 대상과 사용 상황

| 대상 | 상황 | 원하는 결과 |
|---|---|---|
| 주 보호자 | 아기를 안고 울음 원인을 살피는 중 | 한 화면에서 다음 확인 행동과 근거를 이해한다 |
| 평소 기록하는 보호자 | 수유나 재우기를 마친 직후 | 짧게 기록하고 나중에 수정한다 |
| 공동양육자 | 다른 보호자에게 돌봄을 넘겨받는 중 | 같은 아기의 최근 행동과 반응을 보고 이어서 돌본다 |
| 해커톤 체험자 | 처음 접속해 서비스를 시험하는 중 | 준비된 예시와 직접 입력의 차이를 알고 전체 흐름을 체험한다 |

기획상 생후 0~6개월 영아 보호자를 첫 대상 후보로 둔다. 모델이 지원하는 월령은 평가 자료에 따라 따로 표시한다. 한 기기에서 선택된 아기 1명을 관찰하며, 여러 아기나 TV 속 울음을 자동으로 식별하는 기능은 P0에 포함하지 않는다.

### 검증할 가설

- H1: 울음 후보와 최근 기록을 함께 보여주면 보호자가 다음 확인 행동을 고르기 쉬워진다.
- H2: 행동과 반응 기록을 짧게 만들면 울음 사건 후에도 기록을 남길 수 있다.
- H3: 같은 아기의 과거 사례가 충분할 때 그 기록을 참고한 안내가 도움이 된다.
- H4: 기록에 근거한 준비 알림이 유용하다. 실제 울음 감소 효과는 별도 연구가 필요하다.
- H5: 선택지와 자연어를 함께 제공하면 기록 부담을 줄이면서 학습에 필요한 관찰을 구조화할 수 있다.
- H6: 공동양육자가 같은 이력을 보면 돌봄 인계 시 누락과 중복 확인을 줄일 수 있다.

## 3 제품 원칙

**관찰과 추정을 구분한다.** ‘수유 후 진정됨’은 관찰이며 ‘배가 고팠음’의 확정 정답이 아니다. 모델 후보, 보호자의 행동, 관찰된 반응, 보호자의 해석을 각각 저장한다.

**돌봄 중에도 짧게 사용할 수 있게 한다.** 우선 행동 1개와 다른 선택지 1~2개를 보여준다. 분석을 기다리는 동안에도 기록하거나 화면을 나갈 수 있다. 녹음을 마치기 위해 돌봄을 늦추도록 요구하지 않는다.

**정보가 없으면 없다고 말한다.** 기록 누락, 녹음 품질 저하, 미지원 입력, 모델 판단 유보를 구분한다. 미응답이나 감지 중단 시간을 ‘아기가 울지 않은 시간’으로 채우지 않는다.

**개인화의 근거를 보여준다.** 참고한 기록의 시각과 유사 사례 수를 보여주며 사용자가 기록을 고치면 안내를 다시 계산한다. 단순 기록 반영을 모델 재학습이나 정확도 상승으로 표현하지 않는다.

**라벨의 출처와 확인 상태를 보존한다.** LLM은 보호자가 쓴 내용을 정리한다. 입력하지 않은 행동이나 원인을 만들어내지 않는다. 원문, 선택값, 정규화 초안, 확인 및 수정 이력은 서로 연결하되 역할을 구분한다.

**아기를 중심으로 공유한다.** 같은 아기에 대한 맞춤 안내는 공동 기록을 참고한다. 계정 비밀번호를 공유하지 않으며 작성자, 실제 시각과 마지막 동기화 시각을 확인할 수 있게 한다.

### 이번에 완성할 핵심 경험

‘지금 분석’, ‘감지 시작’, ‘빠른 기록’, ‘오늘의 기록’을 홈에서 찾을 수 있어야 한다. 분석이 불확실해도 최근 기록을 확인하고 실제 행동을 남기는 흐름은 완결돼야 한다. 준비 알림은 조건을 만족한 기록에만 제공하며, 조건 미달 화면도 정상 기능에 포함한다. 기록에는 선택지와 자연어 입력을 함께 제공하고, 정규화된 내용의 확인·수정과 상태 그래픽을 연결한다. 초대받은 공동양육자는 같은 사건에 후속 행동과 반응을 남길 수 있어야 한다.

### 확장으로 두는 경험

모바일 화면 잠금 중 상시 감지 보장, 울기 전 실제 발생 확률 표시, 자동 학습으로 매번 정확도 향상, 영상 상태 판정, 질병 진단, 가전 자동 제어는 첫 시제품의 성과로 제시하지 않는다. 자유 대화형 챗봇보다 정해진 기록과 요약의 정확성을 먼저 완성한다.

## 5 주요 사용자 여정

### J01 처음 울음을 분석하는 보호자

1. 보호자가 로그인하고 아기 별칭, 생년월일, 수유 방식과 시간대를 설정한다.
2. 분석 동의 후 ‘지금 분석’을 누르고 마이크를 허용한다. 녹음 상태와 종료 버튼이 보인다.
3. 품질과 울음 여부를 확인한다. 조건이 맞으면 오디오 원인 후보를 분석한다.
4. 최근 생활 기록이 없으면 그 사실을 표시하고 확인할 정보 최대 2개만 선택적으로 묻는다.
5. 원인 후보, 참고 정보, 우선 확인 행동을 보여준다. 보호자는 다른 행동을 선택할 수 있다.
6. 실제 행동과 상태·반응을 선택지 또는 자연어로 입력한다. 정규화 초안을 확인해 저장하면 상태 그래픽과 공동 타임라인에 반영된다. 나중에 추가 반응을 남길 수 있다.

성공 조건은 특정 원인을 반드시 맞히는 것이 아니라, 분석 한계를 이해한 보호자가 행동과 관찰을 남길 수 있는 것이다. 원인 분류 성능은 별도 지표로 평가한다.

### J02 감지 세션에서 같은 울음이 이어지는 경우

1. 보호자가 기기를 아기 가까이에 두고 화면을 켠 채 감지를 시작한다.
2. 브라우저에서 울음 후보를 찾고 짧은 구간만 분석한다. 이어지는 울음은 한 사건으로 묶는다.
3. 결과를 한 번 안내하고 기록을 연결한다. 같은 사건의 소리 때문에 알림을 반복하지 않는다.
4. 화면이 숨겨지거나 입력이 끊기면 지원 정책에 따라 감지를 일시중지하고 관측 공백을 기록한다.
5. 화면으로 돌아왔을 때 마지막 정상 수신 시각과 재개 버튼을 보여준다.

웹에서도 활성 페이지에서 연속 감지가 가능하다. 다른 탭과 잠금 상태의 동작은 브라우저와 운영체제에 영향을 받으므로 P0는 전경 세션만 지원한다. 숨김 시 중지는 이 제품의 보수적인 지원 정책이며 모든 브라우저가 즉시 녹음을 중단한다는 뜻은 아니다. PWA 설치만으로 백그라운드 마이크 보장이 생기지는 않는다. [S04–S06]

### J03 누락된 수유 기록을 수정하는 경우

오디오 후보와 ‘마지막 기록된 수유’가 현재 상황과 다르면 보호자가 누락된 수유를 입력한다. 시스템은 새 맥락으로 확인 행동을 다시 계산하고 바뀐 이유를 보여준다. 이전 분석 당시의 기록과 안내는 이력으로 보존한다. 수정 후 새 안내를 ‘과거에 이미 알고 있었던 결과’로 덮어쓰지 않는다.

### J04 평소 기록과 준비 알림

울음이 없어도 수유, 잠들기와 깨어남, 기저귀 확인 및 교체를 기록한다. 홈에는 최근 기록과 기록된 수면 합계를 보여준다. 충분한 완결 기록이 있을 때만 최근 기록 간격에 근거한 준비 알림을 제안한다. 알림을 끄거나 미룰 수 있고, ‘곧 울 확률’로 표시하지 않는다.

### J05 자연어를 학습 후보 라벨로 남기는 경우

보호자가 ‘안아도 계속 울어서 분유 80ml를 먹였고 10분 뒤 잠들었어요’라고 입력한다. 시스템은 안기와 수유를 순서대로 나누고 ‘계속 욺’과 ‘잠듦’을 관찰로 정리한다. 시작 시각이 없으면 질문하거나 시각 미상으로 남긴다. 보호자는 확인 화면에서 순서와 양을 고쳐 저장한다. 잠듦 그래픽에는 ‘보호자가 기록한 상태’와 관찰 시각을 표시한다.

공통 모델 개선에 필요한 동의와 음원 이용 조건이 충족되면 해당 자료를 검수 대기 후보로 연결한다. ‘수유 후 잠듦’을 배고픔 확정 라벨로 바꾸지 않는다. 모델 학습, 평가, 새 버전 배포는 이 후보를 검수한 다음 단계다.

### J06 공동양육자가 이어서 돌보는 경우

관리 보호자가 아기 설정에서 초대 링크를 만들고 직접 전달한다. 초대받은 사람은 본인 계정으로 로그인해 참여를 수락한다. 최근 수유와 울음 사건, 확인된 상태 및 작성자가 함께 보인다. 다른 보호자가 추가 행동을 저장하면 활성 화면은 새 기록을 반영하고 안내 갱신 여부를 표시한다. 같은 기록의 동시 수정은 충돌로 알려 조용히 덮어쓰지 않는다.

## 7 AI와 개인화 설계

### 오디오 모델

M2D를 중심으로 울음 표현과 보호자 보고 라벨을 학습한다. 울음 감지기는 원인 분류기와 목적이 다르므로 비울음 자료를 포함해 따로 검증한다. 모델은 지원 라벨, 후보 점수, 품질 상태, 판단 유보 이유와 버전을 반환한다. 통증 관련 연구 라벨을 의료 진단으로 표시하지 않는다. [S01–S03]

BABYCRY의 재사용 권한은 최신 학습 계획에서 아직 확인되지 않은 항목이다. 주 학습 경로를 실제 수행하기 전에 사용 조건을 기록한다. 권한이나 학습이 준비되지 않은 동안 화면과 API는 명시된 테스트 응답으로 개발할 수 있지만, 이를 실제 M2D 학습 완료로 발표하지 않는다.

### 개인화의 세 단계

| 단계 | 구현 | 사용자에게 설명할 변화 |
|---|---|---|
| 기록 반영 | 최근 기록과 누락 상태를 조회 | 수정한 기록을 안내에 반영 |
| 아기별 사례 활용 | 같은 아기의 이전 사건과 반응 조회 | 이 아기의 이전 관찰을 참고 |
| 모델 개선 | 동의 자료 검수 학습 비교 평가 새 버전 배포 | 검증한 평가에서 개선된 결과 |

P0는 앞의 두 단계와 세 번째 단계의 라벨 수집·검수·내보내기 준비까지 구현한다. 운영 중 자동 재학습은 후속 단계다. 맥락은 명시적 규칙과 사례 조회로 결합한다. 오디오 후보 순위와 생활 기록에 따른 행동 우선순위를 별도로 유지해, 규칙으로 바꾼 행동을 ‘오디오 모델이 알아맞힌 원인’이라고 표시하지 않는다.

새 학습 자료에서는 같은 사건의 오디오, 분석 당시 알려진 맥락, 실제 행동, 반응, 추천 노출 여부를 연결한다. 나중에 입력한 정보나 분석 이후의 행동을 최초 예측 입력에 섞지 않는다. 합성 육아 기록과 공개 울음 파일을 조합한 예시는 실제 결합 학습 자료로 계산하지 않는다.

### LLM 정규화와 학습 데이터의 경계

선택지는 고정된 표준 코드로 연결하고 자연어 및 혼합 입력은 LLM API로 구조화한다. LLM에는 해당 입력과 필요한 시각·선택값만 보내고, 오디오 모델의 원인 후보나 추천을 정답 힌트로 넣지 않는다. 정해진 출력 형식, 허용 라벨, 원문 근거를 서버에서 검증한다. 구조가 맞는 출력도 의미를 잘못 해석할 수 있으므로 보호자가 확인하거나 수정한다. [S11]

실제 행동, 관찰한 상태, 행동 후 변화, 보호자의 원인 해석은 별도 라벨이다. 부정, 계획, 가정, 복합 행동과 모르는 시각을 보존한다. 학습 후보에는 음원과 당시 맥락, 입력·정규화·확인 버전, 작성자와 확인자, 동의 범위, 추천 노출 이력을 연결한다. 의미 확인이 안 된 자료와 여러 행동의 효과를 분리할 수 없는 자료는 그 한계를 표시한다.

이번 구현의 완료 기준은 자료를 남기는 데서 끝나지 않는다. 권한을 가진 검수 담당자가 적격 자료만 버전 있는 묶음으로 내보내고, 철회 및 수정 시 영향을 받는 묶음을 추적할 수 있어야 한다. 공통 학습에는 아기 단위 참여 설정과 포함 자료 작성자들의 참여 동의가 모두 필요하다. 데이터가 늘었다는 사실만으로 번역 성능 개선을 주장하지 않는다.

## 8 울음 전 예측의 구현 판단

### P0에서 가능한 것

생활 기록의 대표 간격과 최근성을 이용해 ‘최근 기록상 수면 준비를 확인할 시점이 가까워요’ 같은 안내를 제공한다. 기록 범위와 건수를 함께 보여준다. 처음에는 사용자가 알림을 켠 항목만 홈과 활성 화면에서 안내한다.

### 후속 연구가 필요한 것

‘앞으로 30분 안에 울 확률’은 별도의 예측 문제다. 모델을 만들려면 울었던 순간뿐 아니라 실제로 관찰 중이었으나 울지 않았던 시간, 감지 공백, 돌봄 행동과 시각이 필요하다. 창 시작 시점까지 알려진 정보만 입력하고 이후 울음 발생을 평가해야 한다.

관측이 중간에 끊긴 창은 정상 비울음으로 채우지 않는다. 알림을 보고 보호자가 행동해 울음이 발생하지 않은 경우에는 개입 여부를 기록한다. 울음 발생 예측이 맞는 것과 알림이 울음을 줄이는 효과가 있는 것은 별도 평가다.

다음 조건을 모두 충족한 뒤 사용자에게 확률을 표시하는 기능을 검토한다: 관측 시간과 사건 라벨 확보, 아기 및 시간 분리 평가, 확률 보정 평가, 오경보 부담 측정, 전향적 검증. 이번 해커톤에서는 이 경로를 확장성으로 설명한다.

### 권장 배포 구성

| Cloud Run | FastAPI 오디오 추론 맥락 및 라벨 처리 | CPU 실측 LLM 키와 요청량 제한 |
| LLM API | 자연어를 행동 상태 반응 라벨로 정리 | 서버 경유 구조와 의미 검증 실패 복구 |

브라우저에서 가벼운 후보 감지를 수행하고 분석할 짧은 음원만 비공개 저장소에 보낸다. 서버는 사용자 권한을 확인한 파일만 읽고 결과와 분석 당시 맥락을 저장한다. 모델은 서버 시작 때 한 번 준비한다. 요청마다 학습하거나 가중치를 다시 내려받지 않는다.

P0는 짧은 분석을 요청이 살아 있는 동안 완료하는 방식으로 단순화한다. 요청 종료 후 메모리 안에서만 작업을 계속하는 방식은 쓰지 않는다. 처리 상태는 DB에 남겨 연결이 끊겨도 조회할 수 있게 하고, 제한 시간 초과는 실패 상태와 재시도로 처리한다. 장시간 분석이 필요해지면 내구성 있는 작업 큐로 옮긴다.

개발 환경은 필요할 때 실행하고, 시연 전에는 인스턴스를 준비해 첫 응답 지연을 점검한다. 인스턴스 수, 동시 추론 수와 요청량에 한도를 둔다. 유료 자원과 비용 알림은 실제 사용량에 따라 설정한다. 무료 플랜이나 낮은 비용만으로 시연 안정성이 보장된다고 가정하지 않는다. [S07–S09]

### 데이터 책임

원시 오디오, 아기 정보, 생활 기록은 아기 단위로 격리하고 활성 구성원 권한을 확인한다. 계정 간 연결은 아기의 공동 공간에 대한 참여이며 계정 병합이 아니다. 공동 기록에는 작성자와 수정 이력을 남기고, 입력 중인 개인 초안은 확인 저장 전까지 다른 구성원에게 공개하지 않는다. 분석에 필요한 임시 처리, 사용자가 원한 재생용 보관, 공통 모델 개선 참여를 분리한다. 기록 수정과 삭제는 요약 및 개인화 조회에도 반영한다. 음원뿐 아니라 원문, 정규화 결과, 해당 아기의 특징값과 학습 대기 자료도 삭제 범위에 포함한다. 관리 보호자만 전체 아기 데이터를 삭제할 수 있으며 공동양육자의 나가기는 공유 기록 삭제와 구분한다. 연결 해제 시 이후 접근을 차단하고 이미 발급한 파일 접근 경로의 짧은 유효기간도 명시한다.

| 추론 지연 | 업로드 완료부터 결과 저장까지의 p95 | 예열된 시연 환경 15초 이내 목표 |
| 감지 안정성 | 지원 기기에서 입력이 실제 유효한 시간 | 30분 세션과 중단 복구 시험 통과 |
| 분류 성능 | 그룹 분리 macro F1 범주별 재현율 혼동행렬 | 다수 클래스 기준과 비교해 보고 |
| 판단 유보 | 유보율과 답한 표본에서의 오류율 | 적용한 임계값과 표본 수 공개 |
| 기록 효과 | 오디오만 맥락만 결합 사례추가 조건 비교 | 개선 여부를 측정 후 설명 |
| 데이터 보호 | 비구성원 및 해제된 구성원 접근 삭제 시험 | 권한 우회와 삭제 잔존 결함 없음 |
| 라벨 정규화 | 사람 검수 정답과 필드별 일치율 및 수정률 비교 | 부정 계획 누락 복합 입력 시험 통과 |
| 공동 기록 반영 | 한 계정 저장부터 다른 활성 화면 표시까지 | 정상 연결 p95 5초 이내 목표 |
| 학습 준비도 | 적격 후보 내보내기 재로딩 수정 철회 추적 | 근거 없는 원인 라벨과 권한 누락 없음 |

분류 정확도 하나로 판단하지 않는다. Donate-a-Cry의 라벨 불균형과 보고 라벨의 한계를 고려한다. 동일 녹음과 파생 파일은 같은 평가 그룹에 두며, 앱 설치 ID를 아기 ID로 취급하지 않는다. 새로운 아기에서의 성능을 말하려면 실제 아기 단위 평가 자료가 필요하다. [S02]

개인화 비교는 A 오디오만, B 맥락만, C 오디오와 맥락, D 이전 사례 추가로 나눈다. 개발용 가상 시나리오는 안내 규칙의 동작을 확인하고, 실제 관찰 자료는 성능과 사용성을 평가한다. 두 결과를 합산하지 않는다. ‘수유 후 진정’ 비율은 관찰 집계이며 원인 정확도나 인과 효과로 계산하지 않는다.

## 11 출시 단계와 책임

| 단계 | 주 산출물 | 종료 조건 | 책임 역할 |
|---|---|---|---|
| M0 계약 고정 | 화면 흐름 입력 스키마 모델 인터페이스 | P0 범위와 실제 및 예시 모드 명확 | 제품 개발 ML |
| M1 공동 기록 기반 | 로그인 초대 프로필 생활 기록 타임라인 | 구성원 권한 수정 중복 방지 삭제 통과 | 개발 |
| M2 분석과 라벨 연결 | 녹음 추론 선택 및 자연어 입력 상태 그래픽 | 정규화 확인 행동과 반응 연결 통과 | 개발 ML 디자인 |
| M3 맥락과 감지 | 활성 감지 개인화 요약 준비 알림 | 기록 수정 재계산 및 중단 복구 통과 | 개발 디자인 |
| M4 시연과 학습 준비 | 배포 평가 적격 데이터 내보내기 시연 | 두 계정 시연 복구 철회 추적 검증 | 제품 QA 운영 |

각 역할은 책임 영역이며 별도 인원 수를 요구하지 않는다. 일정이 부족하면 P1과 확장 시연을 먼저 줄인다. P0 감지, 분석, 행동 및 반응, 데이터 통제를 빼는 경우 제품 범위를 변경한 것으로 기록한다. 미완성 기능을 동작하는 것처럼 시연하지 않는다.

### 공개 전 반드시 해결할 항목

- 모델 담당: 데이터 이용 조건과 모델 가중치 배포 조건, 지원 라벨과 입력 범위를 기록한다.
- 제품 담당: 해커톤 일정과 규칙, 대상 월령 표현, 시연 및 공개 이용 범위를 확정한다.
- 개발 담당: 실제 브라우저 버전과 녹음 형식, CPU 추론 지연, 업로드 및 삭제 동작을 검증한다.
- 운영 담당: 데이터 보관 설정, 비용 한도, 장애 복구, 외부 연동 키와 배포 환경을 확인한다.

## 13 확장 설계

### 네이티브 앱과 관찰 기기

계정, 아기, 기록, 분석 API는 웹과 앱에서 함께 사용한다. 네이티브에서는 운영체제별 마이크와 알림 조건을 검증한다. 전용 카메라나 마이크 장치가 관측을 맡고 보호자는 앱이나 웹에서 결과를 보는 구조도 지원할 수 있게 한다.

적외선 카메라는 어두운 환경의 관찰 입력 후보이며, 적외선 영상만으로 체온이나 의료적 상태가 확인되는 것으로 표현하지 않는다. 모든 기기 입력은 출처, 촬영 또는 측정 시각, 수신 시각, 품질, 권한과 유효 범위를 포함한다. 오디오와 영상 결합 모델은 동기화된 자료 확보 후 평가한다.

### 다양한 발성과 육아 맥락을 결합한 기분 추론

울음 외에 옹알이, 웃음, 칭얼거림, 기타 발성을 구분한 뒤 최근 수유·수면·상호작용과 보호자 관찰을 함께 활용해 기분 후보를 제시한다. 발성 종류, 추정한 정서, 욕구 후보를 별도 출력으로 둔다. ‘옹알이니까 즐거움’처럼 발성 하나를 기분의 정답으로 대응시키지 않는다.

확장 데이터에는 발성 구간과 시각, 월령, 주변 소음, 상호작용, 보호자 관찰과 불확실성을 담는다. 아기와 가정 단위로 분리한 평가, 오디오 단독 대비 맥락 결합 평가와 사용자 이해 검증 후 출시한다. P0 상태 그래픽은 보호자가 입력한 관찰을 표현하는 기능이며, 이 후속 자동 기분 추론이 구현됐다는 표시로 사용하지 않는다.

### 가전 연결

TV, 스피커, 에어컨, 분유제조기는 기기별 연동 어댑터를 둔다. 상태 읽기, 행동 제안, 사용자의 실행 확인, 기기의 완료 응답을 분리한다. 처음에는 읽기와 제안부터 확장하고, 실제 제어는 지원 기종과 명령별 조건을 검증한 뒤 추가한다. 통신 응답이 없으면 실행 완료로 표시하지 않는다.

## 14 해커톤 시연 기준과 참고 자료

시연은 ① 두 보호자 계정의 같은 아기 연결 ② 직접 입력 또는 활성 감지 ③ 실제 분석 후보와 공동 기록 ④ 선택지·자연어로 복합 행동과 상태 입력 ⑤ LLM 정규화 확인과 상태 그래픽 ⑥ 다른 보호자 화면 반영 ⑦ 동의한 예시 자료의 학습 후보 구조 확인 순서로 구성한다. 별도 준비한 가상 기록에는 예시 표시를 유지한다. 예측, 다양한 발성의 기분 추론과 IoT는 구현 여부를 구분해 후속 로드맵으로 설명한다.

완료 판정은 기능명세서의 P0 인수 기준, 실제 배포 접속, 모델 및 데이터 버전 기록, 사용 기기의 녹음 검증을 모두 충족했을 때 한다. 모델 성능이 부족하면 원인 후보 노출을 줄이거나 유보하고 실제 결과를 보고한다.

### 문서 간 기준

제품 범위와 우선순위는 이 PRD, 화면 동작과 상태 및 API 계약은 기능명세서, M2D 학습 절차는 기존 로컬 학습 계획을 따른다. 이전 설계안의 Dasheng 중심 순서와 이 문서가 다를 때는 최신 M2D 학습 계획을 적용한다. 변경 시 두 문서의 요구사항 ID를 함께 갱신한다.

### 개정 이력

버전 1.1은 R14~R17, F17~F20, SC09~SC10을 추가했다. 공동양육을 P1에서 P0로 이동하고 사용자 소유권 중심 접근을 아기 구성원 중심으로 변경했다. 라벨 정규화와 학습 후보 준비를 P0로 명시했다. 기존 M2D 로컬 학습 계획은 오디오 모델 경로에 계속 적용하며 서비스 라벨 수집과 공동양육 계약은 이 버전과 기능명세서를 따른다.
