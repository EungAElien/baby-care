# Baby Care 코딩 및 협업 컨벤션

> 팀원이 같은 기준으로 구현·검토하고, 보호자와 아기의 데이터를 안전하게 다루기 위한 규칙입니다.

**적용 범위:** `baby-care/`의 웹, API, 계약, Supabase 설정, 문서와 GitHub 협업

**문서 관계:** 제품 범위는 [PRD v2](../baby-care-prd-v2.docx), 기능 동작과 인수 조건은 [기능명세 v2](../baby-care-functional-spec-v2.docx), 연동 필드·상태·권한·오류는 [개발계약](../../contracts/개발계약.md)과 [OpenAPI 계약](../../contracts/openapi계약.json)을 따릅니다. 이 문서는 구현 방식과 협업 규칙을 정하며, 계약 값을 임의로 바꾸지 않습니다.

## 프로젝트 구조와 담당

```text
baby-care/
├─ apps/web/             A: Next.js 웹·브라우저 화면
├─ apps/api/             B: FastAPI·서비스용 모델 추론
├─ contracts/            OpenAPI·합성 목 응답·계약 생성/검증
├─ supabase/             B: 설정·DB 마이그레이션·RLS·Storage 정책
├─ docs/                 PRD·기능명세·A/B 작업표·보안 문서·팀 규칙
└─ .github/workflows/    웹·API·계약 자동 검사
```

- A는 웹 화면, 브라우저 오디오, 클라이언트 상태와 웹 통합 시험을 맡습니다. B는 API, DB·권한, 모델·정규화와 서버 운영을 맡습니다. `contracts/`는 공동 연동 경계이며 B가 스키마·샘플을 수정하고 A가 웹 영향을 확인합니다.
- 현재 `apps/web/`에는 초기 기반과 테스트가 있고 `contracts/`에는 계약·합성 자료·검증 스크립트가 있습니다. `apps/api/`, `supabase/`, `.github/workflows/`는 현재 자리 표시자입니다. 이 트리의 설명은 **담당과 목표 구조**이며, 해당 기능이나 CI가 이미 동작한다는 뜻이 아닙니다. 작업을 시작할 때 실제 파일과 설정을 다시 확인합니다.
- 작업 항목은 [A 작업표](../baby-care-implementation-tasks-A-v2.md), [B 작업표](../baby-care-implementation-tasks-B-v2.md)에서 찾습니다. 보안 설계와 시험 항목은 `docs/security/`에 있습니다. 보안 문서의 새 API 제안이나 미실행 시험은 확정 계약·통과 결과로 취급하지 않습니다.

## 1. 작업과 브랜치

- `main`은 배포 가능한 안정 버전, `develop`은 개발 결과를 통합하고 연동을 확인하는 브랜치입니다. `develop`은 `main`에서 생성합니다. 아직 생성되지 않았다는 현재 상태가 이 브랜치 전략을 바꾸지는 않습니다.
- 일반 작업은 최신 `develop`에서 목적별 브랜치를 만들어 진행하고 PR로 `develop`에 병합합니다. 배포할 때는 `develop`에서 `main`으로 PR을 만듭니다. `main`과 `develop`에 직접 push하거나 공유 브랜치를 force push하지 않습니다.
- 브랜치 형식은 `종류/이슈번호-영역-작업`입니다. 이슈가 없으면 번호를 생략합니다. 영문 소문자·숫자·하이픈을 씁니다.
- 종류는 `feature`, `fix`, `chore`, 긴급 배포 수정은 `hotfix`를 사용합니다. 영역은 `web`, `api`, `contract`, `supabase`, `docs`처럼 변경 위치가 드러나게 씁니다.

```text
feature/12-web-audio-upload
fix/27-api-membership-check
chore/contract-generate-types
hotfix/42-api-invite-expiry
```

### 브랜치 역할

| 브랜치      | 역할                            | 생성 기준        | PR 대상                         |
| ----------- | ------------------------------- | ---------------- | ------------------------------- |
| `main`      | 배포 가능한 안정 버전           | 초기 저장소 구성 | —                               |
| `develop`   | 개발 결과 통합 및 연동 확인     | `main`           | 배포 시 `main`                  |
| `feature/*` | 기능 추가·개선                  | 최신 `develop`   | `develop`                       |
| `fix/*`     | 개발 중 발견한 오류 수정        | 최신 `develop`   | `develop`                       |
| `chore/*`   | 설정·의존성·문서 등 유지 작업   | 최신 `develop`   | `develop`                       |
| `hotfix/*`  | 현재 배포 버전의 긴급 오류 수정 | 최신 `main`      | `main`, 이후 `develop`에도 반영 |

### 브랜치 이름

```text
브랜치종류/이슈번호-도메인-작업내용
```

- 일반 작업 PR의 대상은 `develop`, 배포 PR의 대상은 `main`입니다. 하나의 PR에는 가능한 한 하나의 목적을 담고, 설계 의견이 먼저 필요하면 Draft PR을 엽니다.
- 병합 전 작성자 외 최소 1명이 변경을 검토하고 승인합니다. 필수 수정 의견과 구성된 자동 검사를 해결한 뒤 병합합니다. 자동 검사가 아직 없으면 PR에 수동 확인 결과를 적습니다.
- 작업 브랜치에서 `develop`으로 가는 PR은 **Squash and merge**, `develop`에서 `main`으로 가는 배포 PR은 **Create a merge commit**을 기본으로 합니다. 작업 브랜치는 병합 후 삭제하고 `main`과 `develop`은 유지합니다.
- 긴급 배포 수정은 최신 `main`에서 `hotfix/*` 브랜치를 만들어 PR로 `main`에 반영합니다. 이후 수정 사항이 포함된 `main`을 `develop`에도 PR로 병합합니다.

## 2. 코드 스타일과 이름

### 웹: `apps/web/`

- TypeScript의 `strict`와 `noUncheckedIndexedAccess` 설정을 유지합니다. 타입 오류를 `any`나 무분별한 단언으로 숨기지 않습니다.
- 현재 코드와 같이 공백 2칸, 큰따옴표, 세미콜론, LF 줄바꿈, 파일 끝 개행을 사용합니다. 저장소의 ESLint 설정을 우선합니다. **현재 Prettier 설정은 없으므로** 이전 프로젝트의 공백 4칸·작은따옴표 설정을 그대로 적용하지 않습니다.
- 변수·함수는 `camelCase`, 컴포넌트·타입·클래스는 `PascalCase`, 상수는 의미가 드러나는 이름을 사용합니다. React 컴포넌트 파일은 기존 `app-providers.tsx`처럼 소문자 하이픈 이름을 기본으로 합니다.
- `src/app/`에는 라우트와 화면 구성을, 공통 UI는 `src/components/`, 재사용 로직과 API 경계는 `src/lib/`에 둡니다. 기능 규모가 커지면 관련 파일을 기능별로 묶되 중복된 API·권한 로직을 만들지 않습니다.
- 브라우저 전용 기능에만 `"use client"`를 사용합니다. 개인 자료를 서버 렌더링 결과, 정적 HTML, 공개 캐시에 싣지 않습니다.
- 임시 `console.log`, 사용하지 않는 import·변수·주석 처리된 코드를 제거합니다. 주석은 코드에서 드러나지 않는 이유와 제약을 설명하고, 미완료 TODO는 이슈에 연결합니다.

### API·계약: Python

- `contracts/`의 생성·검증 스크립트와 향후 `apps/api/` 코드는 공백 4칸을 사용합니다. 함수·변수·모듈은 `snake_case`, 클래스는 `PascalCase`로 이름 짓습니다.
- API 구현 시 요청·응답·오류를 Pydantic 모델과 OpenAPI에 맞추고, 예외를 무조건 성공 응답이나 빈 값으로 바꾸지 않습니다.
- Python 포맷터·린터와 API 실행·검사 명령은 `apps/api/`에 실제 설정을 추가할 때 확정합니다. 아직 없는 도구나 명령을 이 문서의 필수 검사로 간주하지 않습니다.

### 전송·데이터 이름

- JSON 전송 필드는 계약대로 `snake_case`입니다. TypeScript 내부 이름을 바꾸더라도 API 필드명과 enum·null 의미를 임의 변환하지 않습니다.
- 날짜·시각은 계약의 시간대 포함 ISO 8601 및 UTC 저장 기준을 따릅니다. `null`(알 수 없음), `0`(실제 영), 미입력을 구분합니다. 음원 길이, 수량, 기간 등의 단위와 경계값을 명시합니다.
- `generated.d.ts` 등 생성 산출물은 수동 수정하지 않습니다. 원본 계약을 수정한 뒤 생성 명령으로 갱신합니다.

## 3. API 계약과 A/B 협업

- `contracts/openapi계약.json`은 웹 연동의 기준입니다. 요청·응답 필드, 필수 여부, enum, 오류 코드, 권한, 상태 전이를 바꾸기 전에 A(웹)와 B(API·데이터·ML)가 영향을 확인합니다.
- B가 계약 원본·샘플을 갱신하고, A가 화면과 생성 타입의 영향을 확인합니다. 계약 변경 PR에는 변경 이유, 호환성, 목 응답, 웹 타입 재생성 및 검증 결과를 함께 적습니다.
- 웹의 업무 데이터 조회·변경은 FastAPI를 통합니다. 브라우저의 Supabase 직접 연결은 계약에서 허용한 Auth, 등록된 private Storage 업로드, 허용된 Realtime 변경 신호로 한정합니다. 업무 테이블 Data API·RPC를 직접 호출하지 않습니다.
- 모든 변경 요청은 계약의 UUID `Idempotency-Key`를 사용합니다. 본문이 있는 요청은 같은 `client_request_id`를 보내고, DELETE는 계약의 `version` 쿼리를 사용합니다. 결과가 불명확한 네트워크 오류를 새 키로 자동 재전송하지 않습니다.
- 화면은 401·403·404·409와 분석의 실패·유보 상태를 구분합니다. 서버 권한과 상태를 화면에서 추측하지 않습니다. 로딩·빈 결과·오류·재시도 가능 여부도 함께 설계합니다.
- 목 응답은 계약과 일치시켜 합성 데이터로만 사용합니다. `REAL`/`STUB` 실행 방식과 `USER`/`DEMO` 데이터 출처를 보존하고, STUB 결과나 DEMO 자료를 실제 모델 검증 결과로 표시하지 않습니다.

## 4. 개인정보·권한·Supabase

- 아기와 계정의 접근 권한은 서버의 현재 멤버십과 아기 상태로 판단합니다. 클라이언트의 역할 표시, 오래된 JWT 역할값, 요청 본문의 사용자 ID만으로 권한을 결정하지 않습니다.
- 웹 캐시와 비동기 응답은 요청 당시 `user_id`·`baby_id` 범위에 묶습니다. 아기 전환, 로그아웃, 멤버십 상실, 탭 복원 시 이전 범위의 요청·캐시·재생 URL·미전송 자료를 계약에 맞게 정리합니다.
- `NEXT_PUBLIC_`에는 공개 가능한 Supabase URL·publishable key·API 주소만 둡니다. `service_role`/secret key, DB·LLM 자격 증명, 실제 토큰·음원·보호자 원문을 소스, 로그, 스크린샷, 목 fixture, PR에 넣지 않습니다. 환경 변수 이름은 `.env.example`로 공유합니다.
- Supabase 업무 테이블·Storage 정책 변경은 재현 가능한 마이그레이션과 함께 검토합니다. 노출 스키마의 RLS, 필요한 GRANT, 아기별 접근 조건을 각각 확인합니다. 서버의 관리자 권한 연결에서도 동일한 멤버십 검사를 수행합니다.
- 권한이 필요한 SQL·Storage·Realtime 변경은 허용 사례뿐 아니라 비구성원, 제거된 구성원, 다른 아기, 만료된 세션의 거부 사례로 검증합니다. 공유·배포 DB의 삭제나 초기화는 영향 범위를 확인하고 팀과 합의합니다.
- 동의, 보관, 삭제는 서로 다른 상태로 처리합니다. 삭제 중인 자료가 늦은 분석·정규화 작업이나 캐시에서 다시 나타나지 않도록 경계를 검증합니다.

## 5. 커밋과 PR

커밋 제목은 `type: 변경 내용` 형식으로 씁니다. `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore` 중 목적에 맞는 타입을 사용합니다. 긴급 수정도 내용에 맞춰 `fix`를 사용하고 브랜치·PR에서 긴급성을 표시합니다.

```text
feat: 아기 전환 시 이전 캐시 정리
fix: 초대 만료 응답 분기 수정
docs: 계약 변경 절차 명시
test: 다른 아기 자료 접근 거부 검증
```

### 타입 목록

| 타입       | 설명                                                        |     |
| ---------- | ----------------------------------------------------------- | --- |
| `feat`     | 새로운 기능 및 화면, 사용자 동작 추가                       |     |
| `fix`      | 잘못된 동작, 화면, 버그 수정                                |     |
| `docs`     | 코드 변경 없이 설명 문서만 수정                             |     |
| `style`    | 논리 및 동작 변화 없는 코드 형식 수정 (포맷팅, 세미콜론 등) |     |
| `refactor` | 논리 및 동작을 유지한 구조 개선                             |     |
| `test`     | 테스트 코드 추가·수정                                       |     |
| `chore`    | 빌드·의존성·공통 설정 등 유지 작업                          |     |

- 커밋은 한 가지 목적에 집중합니다. 동작 변경과 전면 포맷 변경을 섞지 않습니다.
- PR 제목은 `[타입] #이슈번호 작업 내용` 형식을 기본으로 하되 이슈가 없으면 번호를 생략합니다. 관련 이슈는 `Refs #번호`로 연결하고, 종료 시점은 팀의 완료 조건에 따라 판단합니다.
- PR 본문에는 **변경 목적, 주요 변경 사항, 확인 방법과 결과, 리뷰 포인트, 영향과 후속 작업**을 적습니다. 화면 변경은 합성 자료를 사용한 화면 캡처나 재현 순서를, API 변경은 요청·응답 및 오류 사례를 포함합니다.
- 리뷰에서는 동작, 계약 준수, 예외 처리, 권한 경계, 데이터 삭제·보관 영향을 우선 확인합니다. 의견은 `[필수]`, `[제안]`, `[질문]`으로 구분합니다. 이해하지 못한 보안·계산·DB 변경을 승인 요건 충족만을 위해 승인하지 않습니다.
- 새 의존성·환경 변수·DB 마이그레이션·계약 변경은 사용 이유와 적용 방법을 PR에 적고 관련 README와 예시 파일을 갱신합니다.

## 6. 검증 기준

변경 범위에 맞는 검사를 실행하고 PR에 실제 결과를 기록합니다. 실행하지 못한 검사는 이유를 적습니다.

| 변경 범위 | 현재 실행 명령 또는 확인 항목                                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 웹        | `apps/web/`에서 `npm ci`, `npm run typecheck`, `npm test`, `npm run lint`, `npm run build`                                                             |
| 계약      | 저장소 루트에서 `python contracts/build_contract.py`, `python contracts/validate_contract.py`; 이후 `apps/web/`에서 `npm run generate:api`와 타입 검사 |
| API       | 향후 `apps/api/`에 설정한 pytest·정적 검사·빌드 명령. 현재는 미구성                                                                                    |
| Supabase  | 마이그레이션 적용 결과와 RLS·Storage의 허용/거부 시나리오. 현재 프로젝트 설정은 미구성                                                                 |

- 계약 생성은 산출물을 바꾸므로 PR에서 생성 파일의 diff를 확인합니다. `contracts/requirements.txt`와 `apps/web/package-lock.json` 등 해당 잠금·의존성 파일을 함께 관리합니다.
- 중요한 로직에는 정상값, 경계값, 권한 거부, 중복 요청, 응답 유실, 동시 수정, 아기 전환, 삭제 중 늦은 응답 같은 실패 사례를 검증합니다. 모델·LLM의 실제 실행 결과와 합성 목 시험 결과는 구분해 보고합니다.
- 자동화되지 않은 실제 브라우저·두 계정·기기 시험은 재현 절차, 기대 결과, 실제 결과를 남깁니다. 통과하지 않은 범위를 완료로 표시하지 않습니다.

## 7. 기술 결정과 문서 갱신

공통 기술·권한·계약에 대한 의견이 다르면 해결할 문제, 대안, 영향, 공식 근거 또는 작은 시험 결과를 기록하고 영향을 받는 담당자와 결정합니다. 계산 정확성, 데이터 손실, 권한 오류는 다수결로 무시하지 않습니다. 확정한 결정은 계약·작업표·이 문서 중 해당 위치에 반영합니다.

## 8. Codex와 함께 작업할 때

이 파일을 팀원의 Codex에 **저장소 상대 경로** `docs/project-rule/coding-conventions.md`로 먼저 지정합니다. 로컬 PC의 절대 경로는 팀원마다 다르므로 작업 지시나 PR에는 상대 경로를 씁니다.

1. **범위 확인:** 맡은 A/B 작업 번호, 구현할 사용자 흐름, 완료 기준, 제외할 범위를 확인합니다. A 작업표의 ①·②처럼 나뉜 작업은 요청받은 칸을 기준으로 합니다. 명시되지 않은 다음 단계까지 완료했다고 표시하지 않습니다.
2. **현황 확인:** 작업 시작 시 브랜치·미커밋 변경과 관련 파일을 확인합니다. 다른 팀원이나 이전 작업의 변경을 덮어쓰지 않습니다. 이 문서의 구조 표보다 현재 저장소 상태가 새로우면 실제 파일을 기준으로 보고합니다.
3. **기준 읽기:** 제품·동작은 PRD와 기능명세, 연동 세부값은 `contracts/개발계약.md`와 `contracts/openapi계약.json`, 구현 순서와 인수 항목은 해당 A/B 작업표를 읽습니다. 계약과 코드 또는 문서 사이에 충돌이 있으면 관련 담당자에게 차이를 알리고 합의된 변경만 반영합니다.
4. **구현·검증:** 맡은 영역의 코드, 필요한 테스트, 생성 산출물과 문서를 함께 수정합니다. 실제 API·계정·모델·Supabase 환경이 없으면 계약과 `contracts/목 응답과 시험 사용자 배치.json`의 합성 자료로 가능한 범위만 검증합니다. 경로·상태·오류·모델 성능을 추측해서 채우지 않습니다.
5. **계약 인계:** API·DB·권한·환경 변수·의존성을 바꾸면 상대 담당자에게 변경 필드, 이전 값과 새 값, 호환성, 적용 순서, 필요한 재생성·마이그레이션, 검증 결과를 전달합니다. A는 화면 상태와 누락 필드를 B에게 제시하고, B는 확정 스키마와 샘플을 A에게 제공합니다.
6. **결과 보고:** 변경 파일, 실제 실행한 명령과 결과, 미실행·실패한 검사, 목과 실환경의 구분, 남은 수동 확인, 상대 담당자의 후속 작업을 짧게 남깁니다. 코드 작성·목 통과·실기기 검수·실서비스 연동을 서로 다른 완료 상태로 기록합니다.

Codex에 작업을 맡길 때는 다음 항목을 한 요청에 넣습니다. 이 문서와 관련 파일은 Codex가 저장소에서 직접 읽을 수 있으므로 긴 계약 내용을 프롬프트에 다시 복사할 필요는 없습니다.

```text
docs/project-rule/coding-conventions.md를 먼저 읽고 따르세요.
담당/작업: A 또는 B, 작업표 번호와 범위(예: A-03 ①)
목표/완료 기준: 구현할 흐름과 관련 AC·SEC 항목
연동 조건: 실제 API·계정·모델·Supabase 환경의 제공 여부
확인 결과: 실행한 검사, 변경 파일, 목/실환경 구분, 남은 수동 검증과 상대 담당자 인계 사항을 보고
```
