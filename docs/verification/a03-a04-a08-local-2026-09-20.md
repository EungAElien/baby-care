## 발견한 결함과 검증 한계

기존 A-08 폴링은 `invalidateQueries`의 활성 화면 재조회가 끝나기 전에 `current_revision`을 저장했다. 재조회 오류가 나면 다음 폴링이 이미 지나간 revision에서 시작해 화면 갱신을 놓칠 수 있었다. 이제 연결된 `CARE_EVENT`·`BABY`·`MEMBERSHIP` 캐시의 활성 재조회를 기다리고 오류를 전달해 이전 revision에서 재시도한다. tombstone을 먼저 적용한다. 합성 회귀 시험은 첫 재조회 실패 뒤 같은 revision 재생과 성공 뒤에만 전진을 확인했다. 실제 지연·권한·서버 오류 복구는 위 A08 행처럼 미실행이다.

## 실환경 준비와 직접 확인

1. Python 3.12.12 API venv와 잠금 의존성, 루트 Supabase CLI 2.117.0을 준비한다. 기존 고정 프로젝트나 다른 PR 스택을 초기화하지 말고 B-13의 고유 project id·빈 포트 격리 통합 명령을 실행한다. 브라우저 시험에도 독립 로컬 Supabase/Auth/Mailpit, migration·합성 seed, 준비 상태 200인 FastAPI, 공개 설정만 담은 웹 `.env.local`과 별도 웹 포트가 필요하다. 실제 설정값은 이 문서나 Git에 넣지 않는다.
2. Mailpit에서 수신 가능한 서로 다른 시험 이메일로 브라우저 OTP를 직접 검증한다. OWNER가 시험 아기를 만들고 B-04의 새 OTP proof·초대 수락 절차로 CAREGIVER를 ACTIVE로 만든다. 비구성원 404와 다른 CAREGIVER 권한까지 한 번에 검증하려면 세 번째 계정을 비구성원으로 먼저 시험한 뒤 초대해 ACTIVE CAREGIVER로 전환하거나 별도의 네 번째 계정을 사용한다. 현재 A-03 초대 발급·수락 UI는 미연결이므로 해당 구성은 B의 시험 절차/API로 준비하고 브라우저 UI 완료로 오판하지 않는다.
3. A03→A04→A08 순으로 위 표를 두 브라우저에서 확인한다. 변경 저장 응답 완료 시각과 상대 화면 반영 시각을 단조 시계로 여러 표본 기록하고, 전경/숨김/복귀/단절·회복을 별도로 측정한다. 민감 본문·식별자·OTP·토큰 없이 역할 별칭, 환경 버전, 시각, 기대/실제, HTTP 상태·마스킹한 증거 위치만 남긴다. 삭제 COMPLETE는 실행기 준비 후 별도 확인한다.
4. A-03의 미연결 초대 발급·수락, 동의, 재인증·세션 회수 화면은 별도 후속 구현·시험으로 남긴다. Realtime은 SEC30·SEC31 회수 증거 전까지 활성화하지 않는다.
